## 1. 요약 — AI는 무엇을 했고 사람은 무엇을 했는가

### 1.1 역할 분담

```
사람       : 무엇이 좋은 밸런스인가를 정의한다 (지표 M1~M7 · 목적함수 D)
             무엇을 AI에게 맡기지 않을 것인가를 정한다
             AI 산출물의 채택·기각을 판정한다
AI(Claude) : 문서·코드 생성, 스펙 대조, 설계 감사
알고리즘    : 파라미터 탐색(Optuna·SALib) — LLM이 아니다
게임 런타임 : AI 없음
```

- 커밋 태그(`[AI]`/`[H]`/`[BAL]`/`[REV]`)로 이 경계가 저장소에 그대로 남는다
- AI 추천안 중 사람 판단으로 뒤집힌 사례 8건 — 3.3·4.2에서 다룬다
- CI 가드 5종 — 경계, 커밋 규약, 시뮬레이터 결정론, Unity↔core 연동, 전투 불변식

### 1.2 한 줄 요약

AI에게 코드를 짜게 한 프로젝트가 아니라, 무엇을 검증할지 정의하고 그 검증을 자동화한 프로젝트다.

프로젝트 내내 반복된 문제는 하나다 — AI는 "안 되는 것"보다 "되는 것처럼 보이는 것"을 훨씬 잘 만든다. 컴파일되고 테스트가 통과하고 지표가 숫자를 뱉는데, 실제로는 아무 일도 안 일어나거나 틀린 걸 재고 있는 경우가 여러 번 있었다. 그래서 검증 기준을 단계적으로 낮춰왔다(4.3).

### 1.3 사용한 AI 도구

Claude(Claude Code) 하나다. 상세 활용 내역은 8.4에 있다. 탐색에 쓰는 Optuna·SALib는 LLM이 아니라 수치 최적화 라이브러리이며, 이 구분이 2장의 요점이다.

## 2. AI 개발 파이프라인 구조

### 2.1 전체 워크플로

```
 ┌── 사람 ────────────────────────────────────────────────┐
 │  "무엇이 좋은 밸런스인가"를 정의한다                       │
 │     → 지표 M1~M7 · 만족도 함수 · 목적함수 D               │
 └───────────────────┬────────────────────────────────────┘
                     │  (기계가 읽을 수 있는 형태로)
 ┌───────────────────▼────────────────────────────────────┐
 │  /core   순수 C#. 전투·런 루프. UnityEngine 참조 불가     │
 │  /sim    콘솔 앱. params.json → metrics.json             │
 │  /tune   Python. Morris 스크리닝 → Optuna 탐색            │
 │  /unity  렌더링. 이벤트 로그를 재생만 한다                  │
 └───────────────────┬────────────────────────────────────┘
                     │  balance.json (verdict · D · provenance)
 ┌───────────────────▼────────────────────────────────────┐
 │  사람이 판정한다 → [BAL] 커밋 또는 기각                    │
 └────────────────────────────────────────────────────────┘
```

단계마다 쓰는 AI의 종류가 다르다.

| 단계 | 담당 | 하는 일 |
|---|---|---|
| 정의 | 사람 | 지표·목적함수·기각 판정 |
| 생성 | LLM(Claude) | 코드·문서 생성, 스펙 대조, 설계 감사 |
| 탐색 | 알고리즘(Optuna·SALib) | 파라미터 탐색. LLM이 아니다 |
| 실행 | 없음 | 게임 안에 AI가 없다 |

이 루프에는 런타임 LLM 호출이 0건이다. 개발 중 사용하는 LLM도 탐색이 아니라 정의와 판단에만 쓴다.

### 2.2 각 단계에서 사용한 도구와 그 이유

표준 수치 도구는 그대로 썼고, 무엇을 최적화할지는 직접 정의했다.

| 단계 | 채택 도구 | 이유 |
|---|---|---|
| 전역 민감도 분석 | SALib(Morris) | 어느 파라미터를 탐색할지 측정으로 결정 |
| 파라미터 탐색 | Optuna(CMA-ES + ASHA) | ask-and-tell 방식으로 외부 프로세스(`sim`)를 구동 |
| 목적함수 | 직접 작성 | 밸런스 정의 자체이므로 남의 구현에 의존하지 않음 |
| 지표(M1~M7) | 직접 작성 | 같은 이유 |

기각한 도구:

| 검토한 도구 | 기각 사유 |
|---|---|
| LLM을 최적화기로 사용 | 결정론 기반 탐색에 확률적 생성기가 맞지 않음. 재현이 안 됨 |
| BMAD / Spec Kit | 프로젝트 규모에 비해 과함 |
| CMAES.NET | 유지보수가 중단된 라이브러리 |
| OpenSpiel | PvE 단일 플레이어 구조라 적용 조건이 안 맞음 |
| FixedMathSharp | 전부 정수 연산이라 필요 없음 |
| 만족도 함수 라이브러리 | Derringer–Suich 공식이 20줄이면 충분해 의존 추가할 이유가 없음 |

### 2.3 단계 간 산출물 연결

```
/data/*.json  ──→  sim  ──→  metrics.json  ──→  tune  ──→  optuna-*.json
      ▲                                                      │
      └────────  사람이 [BAL] 커밋으로 반영  ←──────────────────┘
                        └→ balance.json (저장소에 남는 스냅샷)
```

`balance.json`의 `provenance` 필드에 커밋 해시·데이터 해시·시드를 기록한다. 어느 커밋의 어느 데이터로 이 결과가 나왔는지 파일 하나로 확인할 수 있다.

## 3. AI 대상 주요 프롬프트 및 지시 사항

### 3.1 프로젝트 전역 규칙

세션마다 자동으로 주입되는 `CLAUDE.md`가 상시 지시문 역할을 한다. 핵심 대목을 그대로 인용한다.

> 커밋은 사후 산출물이 아니라 설계 대상이다. "AI에게 어떤 단위로 일을 시켰고, 어디서 사람이 개입해 판단했는가"가 커밋 메시지와 diff에 드러나도록 처음부터 커밋 전략을 짤 것.
> - 한 커밋 = 하나의 의사결정 단위
> - AI 생성분과 사람 수정분을 가급적 분리 커밋
> - squash / force push 금지
> - 시행착오도 남긴다

> 예선에서 본선으로 넘어가는 유일한 자산은 파이프라인이다. AI 개발 파이프라인은 장르 비의존적으로 설계할 것.

### 3.2 단계별 핵심 지시문 — 원문 인용

D+0~D+1은 저장소가 없던 시기라 지시 원문이 남아 있지 않다. 아래는 그 시점의 판단을 재구성한 것이고, D+2 이후는 실시간 기록(`docs/ai-log/`)이다.

| 시점 | 지시 원문 | 결과 |
|---|---|---|
| D+0 | 게임 아이디어가 아니라 요강에서 역산하라 | 요강을 채점표로 읽는 작업 순서 확립 |
| D+1 | "최적화 관점도 생각해서 어떤 도메인 지식이나 방법을 쓰면 좋을지 조사" | 도구가 아니라 도메인 지식을 요구한 지시. 여기서 밸런스 지표 M4의 정의가 비어 있다는 걸 발견함 |

성공 사례만 나열하면 운으로 읽힌다. 아래는 AI의 판단이 틀렸고 사람이 고친 사례다.

| # | AI의 판단 | 수정 | 유형 |

| 3 | 오픈소스 평가에서 star 수를 그대로 적용 | 실제 영향 범위를 먼저 따지는 절차 추가 | 가치 판단이 기울어 있었음 |

## 4. 사람이 개입한 지점과 그 판단 기준

### 4.1 AI에게 맡기지 않기로 한 영역

| 영역 | 이유 |
|---|---|
| 무엇이 좋은 밸런스인가(지표·목적함수) | AI에게 넘기면 AI가 자기 채점표를 만들게 됨 |
| 구조 수정(데이터 형태 변경) | 최적화기는 값만 바꿀 수 있고 구조는 못 바꿈 |
| 관문 난이도 | 기계에 넘기면 통계적으로 무난한 쪽으로 수렴함 |
| 최적화기 제안의 최종 채택 | 기계는 제안만 하고 사람이 판정함 |

### 4.2 AI 산출물을 되돌린 사례

**설계 추천 14건 중 6건이 뒤집힘.** AI가 낸 전투 규칙 추천안(이동 방식, 거리 계산, 종료 조건, 라운드 간 체력 처리, 적 배치)이 게임 디자인 담당의 확정본과 대조됐을 때 6건이 뒤집혔다. AI 추천은 구현 비용·시뮬레이션 속도 쪽으로 기울어 있었고, 사람 판단은 게임으로 성립하는지를 기준으로 삼았다. 예를 들어 AI는 적을 고정된 격자에 배치하는 안을 냈지만, 실제로는 적도 이동해야 오토배틀러로 성립한다는 판단이 채택됐다.

**밸런스 지표 정의를 사람이 버림.** AI가 구현해둔 지표 해석(지배 빌드 점유율 계산 방식)을 사람이 실측 데이터를 근거로 폐기하고 다시 정의했다. 새 정의로 바꾼 뒤에도 다른 지표를 조정할 때 이 지표가 흔들리지 않는다는 게 같은 날 확인돼, 정정이 옳았음이 실측으로 뒷받침됐다.

**AI가 자기 판단을 스스로 뒤집음.** 런 소요시간 목표치가 계속 미달로 나오자 AI는 "탐색 공간이 부족하다"고 진단하고, 적 스탯 수십 개를 탐색 대상에 추가하자는 안까지 냈다. 이후 근거를 다시 검토하다 그 지표가 전투 시간만 측정하고 있었다는 걸 자기 코드 주석에서 발견했다. 원래 안대로 갔다면 이미 목표에 가까웠던 전투 시간을 몇 배 늘려 영상 길이 제약(30~60초)까지 어겼을 것이다.

### 4.3 검증 기준 — 무엇을 근거로 통과라고 판정했는가

이 프로젝트의 통과 기준은 전부 기계가 판정 가능한 형태다.

| 층 | 기준 |
|---|---|
| 데이터 | 로드 검증 규칙. 실패하면 즉시 에러 |
| 결정론 | 같은 시드로 2회 실행 → 결과 해시 동일(CI) |
| 경계 | `core`에 `UnityEngine` 참조 금지(asmdef + CI 검사) |
| 커밋 | 메시지 규약을 정규식으로 검증(CI) |
| 밸런스 | M1~M7 → 만족도 기하평균 D. 하나라도 0이면 전체 0 |

테스트는 376개(core 337·sim 39)다.

검증 기준은 개발 과정에서 여러 번 더 엄격한 쪽으로 낮춰졌다.

| 단계 | 기준 |
|---|---|
| 1 | 컴파일된다 |
| 2 | 실행된다 — 빌드가 되는 것과 실제로 돌아가는 것은 다름을 확인 |
| 3 | 실제로 쓰인다 — 테스트를 통과해도 실제 루프에서 호출되지 않는 코드가 있었음 |
| 4 | 지표가 그 문제를 볼 수 있는 조건인지 확인한다 — 컴파일·테스트·지표가 전부 정상이어도 실제로는 작동하지 않는 코드가 있었음 |

## 5. 커밋 히스토리로 본 개발 과정

### 5.1 커밋 전략 설계 원칙

```
[주체] type(scope): 요약

의도: <왜 이걸 지금 이렇게 했는가>        ← 모든 커밋 필수
검증: <무엇을 근거로 통과라고 판정했는가>   ← [AI] [BAL] 필수
지표: <M값 before → after>               ← [BAL] [REV] 필수
근거: <시뮬 리포트 경로>                  ← [BAL] 필수
```

규약은 CI가 강제한다. `.git/hooks`는 심사자에게 보이지 않으므로 CI로 검증하는 방식을 택했다.

### 5.2 대표 커밋

| 커밋 | 내용 | 인용 이유 |
|---|---|---|
| `fe8a191` | `[BAL]` 캐릭터 스탯 9개 + 액티브 가격 | 최적화기가 제안하고 사람이 세트째 판정한 첫 사례. 목적함수 D가 0.807 → 0.923으로 이동 |
| `a4a10ab` | `[H]` 런 소요시간 지표 재정의 | AI가 자기 판단을 스스로 뒤집은 사례(4.2 참고) |
| `76f91af` | `[H]` 광역 스킬 발동 주기 조정 | 값이 아니라 구조를 바꾼 수정 — 최적화기가 할 수 없는 종류. 클리어율을 48%에서 33.4%로 이동시킴 |
| `dd0799f` | `[H]` 밸런스 지표 재정의 | AI가 구현해둔 해석을 사람이 버린 기록(4.2 참고) |
| `353e139` | `[AI]` 죽은 유닛이 보드 칸을 계속 점유하는 버그 수정 | 사람이 원인 지점을 짚고 AI가 실제 원인을 찾아 수정 |
| `7e3c166` | `[AI]` 전투 불변식 자동 검사 도입 | 버그를 고친 게 아니라 왜 아무도 못 잡았는지에 답한 커밋. 검증 방식 자체를 바꿈 |

### 5.3 커밋 태그 분포

`[AI]` 113건, `[H]` 109건, `[BAL]` 2건, `[REV]` 2건(병합 68건 별도). AI가 생성하고 사람이 승인만 한 커밋과, AI 산출물에 사람이 직접 손을 대거나 처음부터 사람이 작성한 커밋이 거의 같은 비중으로 나온다 — 사람 개입이 예외적인 경우가 아니라 일상적인 작업 방식이었다는 뜻이다.

## 6. 비용·성능 관리

### 6.1 API 호출 설계

게임 런타임의 LLM 호출은 0건이다. 파라미터 탐색은 Optuna가 로컬에서 무료로 실행한다.

| 항목 | 비용 |
|---|---|
| 게임 실행 | 0 — 브라우저에서 도는 WebGL 빌드, 별도 서버 없음 |
| 밸런스 루프 1회(4,320빌드 21,600런) | 0 — 실행 시간이 초 단위 |

### 6.2 런타임 AI의 지연·실패 처리

해당 없음 — 런타임에 AI를 쓰지 않기로 판단했기 때문이다. 근거는 세 가지다: 결정론 유지(같은 시드는 항상 같은 결과를 내야 밸런스 수치가 의미를 가짐), 심사 조건(별도 유료 라이선스 없이 실행 가능해야 함), 비용(유료 API 비용은 참가자 부담).

## 7. 재현성 및 확장성

### 7.1 파이프라인 이식성

다른 프로젝트로 옮길 때 갈아끼우는 건 지표 목록과 전투 로직 두 가지뿐이다.

| 이식되는 요소 | 장르 의존 여부 |
|---|---|
| 공통 난수, 만족도 함수, 축차 반감법, Morris, `/tune` 분리 구조 | 없음 |
| 결정론 규칙과 CI 가드 | 없음 |
| `/data` 계약 구조(코드에 상수를 박지 않음) | 없음 |
| 커밋 규약과 `[BAL]` 태그 | 없음 |
| 스킬 템플릿, 캐릭터별 밸런스 수치 | 이 게임 전용 — 이식 시 새로 작성 |

### 7.2 48시간 본선에서 이 방식이 어떻게 작동하는가

48시간 해커톤에서 가장 비용이 큰 작업은 코딩이 아니라 밸런스 감을 잡는 것이다. 이 파이프라인은 그 작업을 CI로 옮긴다.

| 시각 | 작업 | 담당 |
|---|---|---|
| 0h | 주제 공개 | — |
| 0~2h | 지표 정의 — "이 게임이 좋다는 게 무슨 뜻인가"를 수치로 정함 | 사람 |
| 2~10h | 전투 로직 구현 | AI 주도 |
| 10h~ | 밤새 CI가 시뮬레이션 실행 | 기계 |
| 다음날 | 결과를 보고 밸런스 패치 판정 | 사람 |
| 30h~ | UI·연출 | 팀 |

예선에서 본선으로 넘어가는 자산은 게임이 아니라 이 작업 순서다.
