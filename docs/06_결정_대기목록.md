**대신 싼 것부터 한다** (게이트 1 전에)

1. **불필요 패키지 제거** — `visualscripting`(로직은 코드·JSON 원칙과 충돌) · `ai.navigation` · `multiplayer.center` · `timeline`
2. **IL2CPP Code Stripping = High**
3. **Shader Stripping** — URP 2D만 남기고 3D 변형 제거
4. **Decompression Fallback** — GitHub Pages는 `Content-Encoding` 헤더를 못 붙인다. **없으면 아예 안 돌아간다**

넷 다 하고도 부족하면 그때 Addressables를 본다. **실측한 숫자가 나온 뒤에.**

### ☑ D-71. `M4` 「지배 빌드 점유율」의 정의 — **C안 확정** (2026-08-04, D+4)

```
M4 = (상위 5% 빌드의 클리어 수 합) / (전체 클리어 수)
     4,320 중 상위 216 개.  균등하면 0.05.  목표 < 0.35
```

`08` §6.2 는 목표만 적어뒀다 — *"최상위 빌드 35% 미만"*. **무엇의 35%인지가 없었다.**
봇이 4,320 빌드를 **똑같이 한 번씩** 돌아 등장 빈도로 재면 어느 빌드든 1/4320 이다.

| 후보 | 판정 | 이유 |
|---|---|---|
| A. 최고 클리어율 | ✗ | 시드 5개라 해상도가 20% 단위고 이미 1.0 으로 포화. **계단 함수라 최적화기에 기울기를 못 준다** |
| B. 클리어 절반을 가져가는 빌드 비율 (D+3 구현) | ✗ | ① 스펙 문장과 **부호가 반대**(높을수록 좋다) ② **`M1` 과 결합** — 아래 |
| **C. 상위 N개의 클리어 점유율** | ✅ | `M1` 과 분리된다. **N=5% 는 사람이 고른 값** |
| D. 지니 계수 | ✗ | N 은 안 정해도 되지만 **스펙의 35% 를 버려야** 하고 설명 비용이 가장 크다 |

> ★ **B 를 버린 결정적 이유는 `M1` 과의 결합이다.** 분모가 전체 빌드 수라
> **게임이 어려워져 클리어 가능한 빌드가 줄면 그 값이 같이 떨어진다.**
> 최적화기가 `M1`(48% → 25~40%)을 고치는 방향이 곧 `M4` 를 깎는 방향이 되어
> **기하평균 안에서 두 지표가 서로 싸운다.** 위반 4건의 뿌리가 "너무 쉽다" 였으므로 정면충돌한다.

`M4` 는 흔들리지 않았다 — **분리가 실제로 작동한다.**
`M4` 를 *"추정이 아니라 정확값"* 이라고 말하는 것이 `D-30` 채택의 결정적 근거였고(`08` §6.1),
**그 근거가 새 정의로도 살아 있다.**

### ☑ D-72. `M6` — **예선 지표에서 제외** (2026-08-04, D+4)

`M6` 은 *"저축 전략(`08` §4.3)이 실제로 작동하는가"* 를 재는 지표다.
**그런데 봇은 저축을 하지 않도록 의도적으로 설계했다** — 그래야 측정 대상이
"빌드 자체의 성립 가능성"으로 깨끗하게 분리된다(`08` §6.1).

```
실측: 첫 활성화 라운드가 2라운드에 92.5% 몰림   ← 봇 정책의 귀결이지 게임의 성질이 아니다
```

**지표와 봇이 서로를 무효화하고 있다.**

| 후보 | 판정 | 이유 |
|---|---|---|
| A. 저축 봇을 따로 둔다 | ✗ | 봇이 둘이 되고 `M6` 만 다른 봇으로 잰 값이라 **다른 지표와 나란히 못 놓는다** |
| B. 사람 플레이로 잰다 | ✗ | 표본이 몇 판뿐이라 분포를 말할 수 없다 |
| C. 재정의한다 | ✗ | 봇 무관하게 잴 수는 있지만 **"저축이 작동하는가" 와 다른 질문**이 된다 |
| **D. 예선 지표에서 뺀다** | ✅ | 못 재는 지표를 목적함수에 넣으면 **최적화기가 봇 정책의 그림자를 쫓는다** |

> **보류가 아니라 제외다.** 값은 리포트에 계속 낸다 — `_notMeasurable` 을 **값 옆에** 박아둬서
> 읽는 사람이 숫자만 보고 *"2라운드에 몰린다"* 로 읽지 않게 한다.
> **무엇을 못 재는지 아는 것이 기록으로 남아야 한다.** 기술 문서에 근거와 함께 적는다.

### ☑ D-74. `M5` 를 맞추려면 최적화기에 무엇까지 허용할 것인가 — **C 확정** (2026-08-04, D+4)

### 🔴 정정 (2026-08-04, 등록 당일) — **이 항목의 최초 근거가 틀렸다**

처음엔 이렇게 적었다:

```
현재  27.6초 / 8라운드 = 3.4초/전투
목표  3분 = 180초      = 22.5초/전투      →  6.5배 필요     ← 틀렸다
```

**전투만 잰 값에 전체 런 목표를 댄 것이다.** `Metrics.M5` 가 스스로 그렇게 적어두고 있었다:

> `"_note": "전투 틱만. 배치·상점 조작 시간은 포함되지 않는다 — 하한으로 읽는다."`

그런데 목표는 `05` §1.8 의 **"1런 3~5분 / 라운드 20~30초"** 이고, **여기서 한 라운드는 상점 + 배치 + 전투다.**

```
전투            0.46분 = 3.4초/라운드      (실측)
조작 추정       15~20초/라운드             (상점 5칸 + 배치)
──────────────────────────────────────
실제 1런        2.5 ~ 3.2분                ← 목표 3~5분의 하단 근처
```

> ★ **부족분은 6.5배가 아니라 0~1.5배 수준이다.** `d`=0.153 은 **잰 것과 목표가 다른 것**이라 나온 값이지,
> 게임이 그만큼 짧아서 나온 값이 아니다.
>
> **`P4` 가 도구로서 잘못된 게 아니라, 내가 지표를 잘못 읽었다.**
> 그리고 이 오독은 **`d`=0.15 라는 낮은 점수로는 절대 안 보인다** — 낮은 점수는
> *"게임이 짧다"* 로도 *"비교 대상이 틀렸다"* 로도 똑같이 읽힌다.
> D+4 의 「지표가 침묵하는 영역」에 **한 항목이 더 붙는다**: <b>지표가 틀린 것을 재고 있어도 숫자는 나온다.</b>

**탐색 공간의 한계는 여전히 사실이다** — 적 스탯이 축 31개 중 0개이고 범위가 ±30% 다.

**정할 것: 최적화기가 게임을 얼마나 다시 빚어도 되는가.**
