## 1. 확정 사항

### 1.1 참가 형태 — 2인 팀

- 제출물이 **5종 전부** 필요하다. 개인 참여 시 생략 가능한 ⑤ 팀원 롤 기술서가 필수가 된다
- ⚠️ **커밋 author 정보와 롤 기술서 내용이 일치해야 한다.** 어긋나면 신뢰도가 통째로 무너진다
  - → 저장소 생성 시점에 **양쪽 git config(`user.name` / `user.email`)를 먼저 맞춰놓을 것.** 나중에 고칠 수 없다
- 역할 분담은 아직 미정 (§4 참조)

### 1.2 제출 형식 — 웹 빌드 (GitHub Pages)

**결정.** 모바일(APK / TestFlight / Play 내부테스트) 루트는 배제한다.

근거:

- 요강 원문이 **"링크 클릭만으로 브라우저에서 바로 플레이"**(`01번` 96줄)를 사실상 표준 경로로 명시
- 모바일 루트는 10일 일정에 **절차 리스크**가 크다
  - TestFlight: Apple 개발자 계정 연 $99 + 심사 대기 1~2일
  - Play 내부테스트: $25 + 개인 개발자 신원 확인(수일 소요) + 심사자 테스터 등록 마찰
  - APK 직배포: 심사자에게 "출처 불명 앱 설치 허용"을 요구하게 됨. 요강이 .exe를 막은 사유가 "보안상"(`01번` 102줄)인데 결이 어긋난다
- "심사 종료 시점까지 링크 유지" 요구를 GitHub Pages는 무료로 자동 충족
- **저장소와 배포가 한 몸**이 된다 → push → 빌드 → 배포 자동화가 그대로 AI 활용 기술 문서 2장(파이프라인 구조) 재료가 됨

### 1.5 AI 활용 축 — 헤드리스 전투 시뮬 기반 자동 밸런스 루프 ★

이 프로젝트의 edge는 여기 하나에 건다.

**구조: 탐색과 디렉팅을 분리한 2층 루프** *(2026-07-31 개정 — 근거는 `13_외부도구_조사.md` §1)*

```
[내부 루프]  파라미터 세트 1개가 주어지면
    → 160개 빌드 전수 시뮬 → M1~M6 계산 → 목적함수 점수
    (전수 탐색이라 추정이 아닌 정확값. 사람도 LLM도 개입 없음)

[외부 루프]  파라미터 공간을 탐색
    → 좌표 하강 + 랜덤 재시작으로 수백~수천 세트 평가
    → 적응적 샘플링: 점수 좋은 후보에 시드를 더 붙이고 나쁜 후보는 일찍 거른다
    (CI에서 돈다. LLM 토큰 0)

[디렉팅 층]  ← 사람 + LLM 이 있어야 할 자리
    → 목적함수를 정의한다 (M1~M6의 목표 구간과 가중치)
    → 탐색 공간을 제약한다 (건드릴 파라미터와 그 범위)
    → 결과를 해석한다 (왜 최적화기가 이 값으로 갔는가)
    → "균형은 맞지만 재미없는 해"를 기각한다
```

> **초안(LLM이 리포트를 읽고 직접 수치 패치를 제안)에서 갈아엎은 것이다.**
> LLM은 수치 최적화기가 아니다. 파라미터 수십 개 공간에서 gradient 없이 헤매고,
> 이터레이션마다 사람 확인이 붙어 10일이면 20~50회가 한계라 **탐색이 성립하지 않는다.**
>
> 선행 연구 확인: **RuleSmith** (arXiv 2602.06232, 2026) 도 같은 문제에 대해
> LLM은 플레이·해석에 쓰고 **탐색은 베이지안 최적화에 맡기는** 구조를 택했다. 적응적 샘플링은 그대로 차용했다.
> 우리는 파라미터 규모가 작아 베이지안까지 갈 필요 없이 좌표 하강으로 충분하다 (≈100줄, 반나절).
>
> **이 분리 자체가 기술 문서 4.1(AI에게 맡기지 않기로 한 영역과 이유)의 핵심 사례가 된다.**
> "AI가 밸런스를 봐줬다"는 활용이고, **"무엇이 좋은 밸런스인지를 정의하고 결과를 기각·채택했다"는 설계**다.
> 대회 메인 카피가 대비시킨 바로 그 두 단어다.

**왜 이 설계인가 (심사 기준과의 대응):**

| 이 설계의 성질 | 대응하는 요강/심사 신호 |
|---|---|
| 밸런스 이터레이션 1회 = 커밋 1개 | "커밋 기록 유지" 요구(`01번` 103줄). 억지 연출 없이 설계된 히스토리가 **자연 발생**한다 |
| 패치했다 나빠져서 revert한 커밋이 남음 | AI 활용 기술 문서 3.3 "실패한 지시와 그 수정 과정"이 자동으로 채워진다 |
| 런타임 LLM 호출 0 | 유료 API 비용 리스크 소거(`03번` 4장). 조영일 센터장 "AI 토큰을 우선순위 판단 단계로 최소화"(`02번` 105줄)와 정확히 동형 |
| 사람이 "무엇을 통과로 볼지" 기준을 정하고 AI가 그 안에서 반복 | 김윤희 이사 "사람이 검증해야 하는 영역에 대한 명확한 기준"(`02번` 103줄)에 대한 직접적 답변 |

→ 심사자가 읽게 되는 문장은 **"AI에게 코드를 짜게 했다"가 아니라 "AI를 밸런스 디자이너 자리에 앉히고 사람이 검증 기준을 설계했다"** 여야 한다.

**⚠️ 이 축이 성립하려면 CI에서 시뮬이 돌아야 한다.** 로컬에서 수동으로 돌려 리포트를 붙이면 같은 얘기지만 설득력이 절반이다. → D+2 게이트 항목 2번.

### 1.6 파이프라인은 장르 비의존적으로 설계한다 ★

**전제: 예선과 본선은 별개의 결과물이다.**

본선은 **주제가 현장에서 공개되고 그 자리에서 48시간 개발**한다(`01번` 154줄). 즉 이 오토배틀러는 본선으로 이어지지 않는다. 본선에서 만들 게임의 장르도, 소재도 지금은 알 수 없다.

→ **예선에서 본선으로 넘어가는 유일한 자산은 파이프라인이다.**

이게 설계 제약을 하나 만든다. §1.5의 밸런스 루프를 **오토배틀러 전용으로 짜면 안 된다.** 다음 형태의 일반 절차로 짜고, 오토배틀러는 그 절차의 첫 번째 적용 사례로 다룬다.

```
1. 게임 로직을 렌더링에서 분리 (헤드리스로 돌아가게)
2. "무엇이 좋은 상태인가"를 수치 지표로 정의      ← 사람이 하는 일
3. 대량 시뮬로 현재 상태 측정
4. AI가 지표를 읽고 데이터 패치 제안
5. 재측정 → 개선 여부 판정 → 커밋               ← 판정 기준은 사람이 정의
6. 반복
```

이 절차에는 "오토배틀러"라는 단어가 없다. 장르가 바뀌어도 2번의 지표 정의만 갈아끼우면 된다.

**비용은 거의 0이다.** 지금 결정해두면 코드 분리 방식이 조금 달라질 뿐이고, 얻는 것은 두 가지다.

- AI 활용 기술 문서 **7.1(다른 프로젝트 이식) / 7.2(48시간 본선 적용 시나리오)** 가 채워진다. `04번` 문서 147줄이 지적하듯 **7.2는 사실상 본선 진출 심사에 대한 직접 답변**이다
- 본선에 실제로 갔을 때 48시간 안에 재사용할 물건이 손에 있다

> 반대로 말하면, 밸런스 루프를 오토배틀러에 용접해버리면 문서 7장을 쓸 수 없고 본선에서도 맨손으로 시작한다. **이 결정은 D+3 코드 착수 전에 확정돼야 한다.**

### 1.7 BM · 수익화 설계는 이 프로젝트 전체에서 제외

- 예선 제출물 5종 어디에도 담을 항목이 없다(`04번` 87줄)
- **본선에도 담기지 않는다.** 본선 결과물은 현장에서 새로 만드는 다른 게임이므로, 이 오토배틀러의 BM은 어디에도 쓰이지 않는다
- 약관 제7조(수상작 사업화 우선협상권 4개월)는 **본선 수상작**에 걸리는 조항이다. 예선 작업 중에 대비할 대상이 아니다
- 운영·BM 설계 역량 자체는 본선 디렉팅 명세서에서 유효한 카드일 수 있으나, **그것은 그때 만들 게임에 대한 것**이다. 지금 이 게임으로 준비해둘 수 있는 건 없다

→ **결론: 지금 BM은 생각하지 않는다. 나중을 위해 남겨두는 것도 아니다.**

## 2. 프로젝트 구조 원칙 (Unity 채택 시 필수)

### 2.1 원칙

| 원칙 | 대신 쓰지 말 것 |
|---|---|
| 씬은 **빈 씬 1개 + 부트스트랩 스크립트 1개**. 나머지는 코드에서 생성 | 씬에 오브젝트 배치 |
| UI는 **UI Toolkit (UXML / USS)** | uGUI 인스펙터 조립 |
| 밸런스·유닛 데이터는 **JSON** | ScriptableObject |
| 프리팹 최소화 | 프리팹 트리 depth 쌓기 |

### 2.2 왜 (이유가 두 겹이다)

1. **AI 기여 범위** — 텍스트 파일이어야 AI가 직접 읽고 쓰고 diff를 낸다
2. **diff 가독성** ★ ← 이쪽이 더 중요하다

에디터 조작용 MCP를 붙이면 1번은 상당 부분 해소된다. 하지만 **결과물은 여전히 `.unity` / `.prefab` YAML 덩어리로 커밋된다.** 사람이 읽을 수 없다.

이 대회는 **심사자가 커밋 히스토리를 실제로 읽는다는 것이 전제**다(`03번` 5장). MCP는 "AI가 UI를 만들 수 있느냐"를 해결하지만 **"그 작업이 심사자에게 보이느냐"는 해결하지 않는다.** 여기서는 후자가 더 중요하다.

→ MCP를 붙이든 안 붙이든 위 원칙은 유지한다. 이유가 "AI가 못 만져서"에서 "diff가 안 읽혀서"로 바뀔 뿐이다.

### 2.3 전투 코어를 Unity에서 분리한다 (`D-12` 확정) ★

**전투 로직을 Unity 비의존 순수 C# 라이브러리로 분리한다. Unity는 그것을 참조해 렌더링·입력·UI만 담당한다.**

```
/core                   ← 순수 C#. UnityEngine 참조 금지
    Domain/               유닛·보드·전투 상태 모델
    Combat/               전투 시뮬레이션 (결정론적)
    Data/                 JSON 스키마 + 로더
    package.json          Unity 로컬 패키지(UPM)로 노출
    Core.csproj           dotnet 빌드용
/sim                    ← 콘솔 앱. core 참조. 대량 시뮬 + 리포트 산출
/unity                  ← Unity 프로젝트. core를 로컬 패키지로 참조
/data                   ← 밸런스 JSON (core / unity / sim 공유)
/.github/workflows      ← 빌드·배포·시뮬
```

**얻는 것 3가지:**

| | 내용 |
|---|---|
| 1 | **게이트 2의 리스크가 사라진다.** 시뮬이 `dotnet`으로 도니 Unity CI 라이선스 활성화가 불필요해진다 |
| 2 | **시뮬 속도가 수십 배.** 밸런스 이터레이션 횟수 = edge의 크기다 |
| 3 | **§1.6(장르 비의존)이 원칙이 아니라 코드 구조로 강제된다.** "게임 로직을 렌더링에서 분리"가 실제 디렉터리 경계가 된다 |

**Unity ↔ core 연결 방식:** core를 **Unity 로컬 패키지(UPM)** 로 참조한다. `manifest.json`에 `"file:../../core"`.

> Unity는 `Assets/` 밖의 코드를 컴파일하지 않는데, 로컬 UPM 패키지는 Unity의 정식 기능이라 심볼릭 링크 없이 이걸 해결한다(Windows에서 symlink는 개발자 모드가 필요해 마찰이 있다).
> **폴백:** UPM 세팅에서 1시간 이상 막히면 `unity/Assets/Core/`에 소스를 두고 `sim`의 csproj에서 `<Compile Include="../unity/Assets/Core/**/*.cs" />` 로 링크한다. 소스는 하나, 컴파일만 두 곳. 이식성은 조금 나빠지지만 5분이면 된다.

**CI 가드: core에 `UnityEngine` 참조가 들어오면 빌드 실패시킨다.**

> AI에게 코어를 짜게 하면 **반드시** `UnityEngine.Vector2`, `Debug.Log`, `Random.Range`를 쓴다. 사람이 매번 잡을 수 없다.
> → CI에서 `core/` 소스에 `UnityEngine` 문자열이 있으면 실패시키는 검사를 넣는다. 몇 줄이면 된다.
> **이건 그 자체로 기술 문서 4장(사람이 개입한 지점) 재료다.** "AI를 신뢰하는 대신, AI가 위반할 수 없는 경계를 CI로 설치했다" — 이 대회가 보고 싶어하는 종류의 서술이다.

### 2.4 전투 시뮬은 결정론적이어야 한다 ★

**같은 시드 → 항상 같은 결과.** 이게 깨지면 밸런스 비교 자체가 성립하지 않는다(패치 전후 차이가 개선 때문인지 노이즈 때문인지 구분 불가).

오토배틀러 전투는 행동 순서 의존이 커서 비결정성이 특히 잘 스며든다. 아래를 코어 작성 규칙으로 강제한다.

| 금지 | 대신 |
|---|---|
| `System.Random` | **시드 주입형 자체 PRNG** (xorshift 등). 구현 의존성 제거 |
| `Dictionary` / `HashSet` 순회 | `List` + 명시적 정렬. 순회 순서가 결과에 영향 주면 안 됨 |
| `DateTime.Now`, `Guid.NewGuid()` | 외부 상태 주입 금지 |
| 부동소수점 누산 순서 의존 | 가능한 곳은 정수/고정소수점. 안 되면 연산 순서를 고정 |

**검증: "같은 시드 2회 실행 → 결과 동일" 회귀 테스트를 CI에 넣는다.** 이게 없으면 밸런스 루프 전체가 모래 위에 선다.

### 2.5 이건 그 자체로 문서 재료다

"왜 이런 프로젝트 구조를 택했나"는 AI 활용 기술 문서 2장(파이프라인 구조) / 4.1(AI에게 맡기지 않기로 한 영역과 이유)에 그대로 들어간다. 구조 선택의 근거가 심사 기준에서 역산됐다는 것 자체가 서술 대상이다.
