## 1. ★ 밸런스 루프 재설계 제안 — 기존 안을 갈아엎는다

### 1.1 발견

**RuleSmith: Multi-Agent LLMs for Automated Game Balancing** (arXiv 2602.06232, 2026)
→ 우리와 **같은 문제를 다룬 2026년 논문**이다.

그 구조:

```
게임 엔진 (튜닝 가능한 파라미터: 팩션·경제·생산·전투)
  + 멀티에이전트 LLM 셀프플레이 (게임을 "플레이"하는 역할)
  + 베이지안 최적화 (파라미터 공간을 "탐색"하는 역할)
  + 적응적 샘플링 (유망 후보엔 많은 판, 탐색 후보엔 적은 판)
```

검증: CivMini(간이 문명류)에서 균형 잡힌 설정으로 수렴, **해석 가능한 규칙 조정**을 산출.

### 1.2 이게 우리 안의 무엇을 지적하는가

`05` §1.5의 내 초안은 이랬다.

```
시뮬 → 리포트 → LLM이 읽고 JSON 패치 제안 → 재시뮬 → 판단 → 커밋
```

**문제: LLM은 수치 최적화기가 아니다.**

- 다차원 파라미터 공간(유닛 스탯 × 스킬 수치 × 경제 = 수십 개)에서 gradient 없이 헤맨다
- 한 이터레이션마다 사람 확인이 붙으므로 10일이면 **20~50회**가 한계다. 그 횟수로는 탐색이 성립하지 않는다
- 사실상 **LLM 직관에 의존한 언덕 오르기**다

### 1.3 대안 — 탐색과 디렉팅을 분리한다

**두 층으로 나눈다.**

```
[내부 루프] 파라미터 세트 1개가 주어지면
    → 160개 빌드 전수 시뮬 → M1~M6 계산 → 목적함수 점수 산출
    (전수 탐색이므로 정확값. 사람도 LLM도 개입 없음)

[외부 루프] 파라미터 공간을 탐색
    → 최적화 알고리즘이 수백~수천 세트를 평가
    (CI에서 무료로 돈다. LLM 토큰 0)

[디렉팅 층] ← 사람 + LLM 이 있어야 할 자리
    → 목적함수를 정의한다 (M1~M6의 목표 구간과 가중치)
    → 탐색 공간을 제약한다 (건드릴 파라미터와 그 범위)
    → 결과를 해석한다 (왜 최적화기가 이 값으로 갔는가)
    → "균형은 맞지만 재미없는 해"를 기각한다
```

**최적화기는 뭘 쓰나** — 베이지안 최적화까지 갈 필요 없다.
파라미터 수십 개 규모면 **좌표 하강(coordinate descent) + 랜덤 재시작**으로 충분하고, 100줄 남짓이다.
RuleSmith의 **적응적 샘플링**은 그대로 차용한다: 점수가 좋은 후보에 시드를 더 붙이고, 탐색 후보는 적은 시드로 거른다.

### 1.4 왜 이게 이 대회에서 더 강한가 ★

대회 메인 카피가 **"활용"과 "설계"를 명시적으로 대비**시켰다.

| | 서술 | 읽히는 수준 |
|---|---|---|
| 기존 안 | "AI가 리포트를 읽고 밸런스 수치를 제안했다" | **활용** |
| 대안 | "탐색은 알고리즘에 맡기고, **무엇이 좋은 밸런스인가를 정의하고 결과를 기각·채택하는 자리**에 사람과 AI를 놓았다" | **설계 / 디렉팅** |

그리고 이 설계는 **정직하다.** LLM이 수치 최적화에 약하다는 걸 알고 그 역할에서 의도적으로 뺀 것 자체가 판단력의 증거다.
기술 문서 4.1(AI에게 맡기지 않기로 한 영역과 이유)에 **가장 강한 사례**가 된다.

부수 효과로 **런타임뿐 아니라 개발 중 LLM 호출도 크게 준다.** 조영일 센터장의 "AI 토큰을 우선순위 판단 단계로 최소화"와 정확히 같은 구조다.

### 1.5 비용

| 항목 | 비용 |
|---|---|
| 최적화기 구현 | 좌표 하강 + 랜덤 재시작 ≈ 100줄. 반나절 |
| 목적함수 정의 | M1~M6에 목표 구간·가중치를 붙이는 작업. **이건 어차피 해야 했다** |
| 리스크 | 최적화기가 "지표는 만족하지만 재미없는" 해로 갈 수 있음 → 그래서 디렉팅 층의 기각 권한이 필수 |

> **권고: 채택.** `05` §1.5를 이 구조로 개정한다.
> 논문은 기술 문서에 **참고문헌으로 인용**한다 — 선행 연구를 확인하고 그 구조를 차용했다는 서술은 신뢰도를 올린다.

**Personal 라이선스는 만료되면 재활성화해야 한다** — 10일 프로젝트라 기간 내에는 문제없지만 D+2 게이트에서 한 번은 겪는다.

### 2.2 FixedMathSharp (결정론 고정소수점) — **불채택**

| 기준 | 평가 |
|---|---|
| 시기성 | NuGet 1.2.0, .NET 대응, 최신 |
| 볼륨 | 적정 (Q32.32 스칼라 + 벡터/행렬) |
| 신뢰성 | 소규모 프로젝트. 채택 실적이 넓지 않다 |

**불채택 사유는 신뢰성이 아니라 "필요 자체가 없다"는 것이다.**

전투 설계(`A-1` 이동 없음 / `A-3` 전열·후열 2단계 사거리)를 확정하면 **부동소수점을 쓸 자리가 사라진다.**

- 거리 = 전열/후열 2단계 → 정수 비교
- 시간 = 고정 틱 정수 누적
- HP·데미지 = 정수
- 확률 = 시드 주입 PRNG의 정수 모듈로

> **의존성을 추가해 결정론을 관리하는 대신, 설계로 결정론이 필요 없게 만든다.**
> 라이브러리 도입 비용 0, 이해 비용 0, 그리고 "왜 고정소수점 라이브러리를 안 썼는가"가 그대로 문서 재료가 된다.
> ⚠️ 단 **`A-1`(이동 없음)이 뒤집히면 이 판단도 뒤집힌다.** 이동이 들어오면 좌표 연산이 생기고 FixedMathSharp를 재검토해야 한다.

### 2.3 오픈소스 오토배틀러 코드 — **참고만. 차용 금지** ⚠️

GitHub에 다수 존재한다 (Unity/C#, Rust+Godot, Python 시뮬레이터, Super Auto Pets 시뮬 엔진 등).
대부분 개인 습작 수준이고 우리 구조(배타 스킬 + 전수 탐색)와 맞지 않는다.

**그리고 라이선스와 별개로 대회 약관 문제가 있다.**

> 약관 제4조 2항: "출품작은 참가자 **본인의 순수 창작물**이어야 하며…"

에셋(이미지·사운드)은 출처 명시로 해결되지만, **게임 코드 베이스를 통째로 가져오는 것은 성격이 다르다.**
→ 구조 참고는 하되 코드는 우리가 쓴다. 실제로 우리 게임은 스킬 템플릿 5종 + 정수 전투라 분량이 크지 않다.

## 3. Unity WebGL 현황 확인 (D+2 게이트 1 리스크 재평가)

| 항목 | 확인된 사실 |
|---|---|
| 최소 빌드 크기 | **빈 프로젝트도 약 8MB** |
| 로딩 | 웹 네이티브 엔진 대비 확연히 느림. 이탈률 상승 요인으로 지적됨 |
| 모바일 브라우저 | 메모리 오버헤드로 불안정 (예상대로 포기가 맞다) |
| 현재 버전 | Unity 6.5 (2026-06). 웹 배포는 계속 개발 중 |
| 압축 | Brotli 권장. **GitHub Pages는 `Content-Encoding` 헤더를 못 붙이므로 Decompression Fallback 필수** |

**→ 기존 판단 유지.** 게이트 1이 여전히 최대 리스크다. 다만 대응책은 명확하다:

1. **Decompression Fallback 활성화** (GitHub Pages에서 gzip/Brotli가 깨지는 전형적 사고를 막는다)
2. 에셋 다이어트 — 8MB가 바닥이므로 우리가 얹는 양을 최소화. **유닛 6종 + 아이콘**이라는 현재 스펙이 여기에 유리하다
3. 로딩 화면을 게임 톤으로 만들어 체감 완화

씬 계층·GameObject·컴포넌트 값·콘솔에 실시간 접근이 되면 **에러 피드백 루프가 닫힌다** — 복붙 왕복이 사라진다. 10일 일정에서 이게 크다.

> ⚠️ **`05` §2.2의 판단은 그대로 유지된다.** MCP는 "AI가 UI를 만들 수 있느냐"를 해결하지만
> **"그 작업이 심사자에게 보이느냐"는 해결하지 않는다.** MCP가 조작해도 결과물은 `.unity`/`.prefab` YAML diff다.
> → **UI Toolkit(UXML/USS) + JSON 데이터 원칙은 유지한다.** MCP는 그 위에서 콘솔·검증용으로 쓴다.

### 4.5.2 SDD 프레임워크 (BMAD / Spec Kit / OpenSpec / GSD) — **불채택. 단 비교 근거로 인용** ★

| 프레임워크 | 규모 |
|---|---|
| [BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD) | MIT, v6.6.0(2026-04), **46,700+ stars**. 12+ 전문 에이전트로 전체 SDLC 오케스트레이션 |
| [GitHub Spec Kit](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/) | GitHub 공식. "intent가 진실의 원천, 명세가 실행 가능" |
| OpenSpec / GSD | 경량 대안 |

**불채택 사유 3가지 — 마지막이 결정적이다.**

1. **볼륨 불일치.** BMAD는 12+ 에이전트로 대규모 그린필드를 다루는 물건이다. 10일·2인·소형 웹게임에 과하다
2. **우리 문서 체계가 이미 SDD다.** `05`(결정) `06`(미결) `08`(스펙) `09`(커밋규약) `12`(분담) + `/data/_schema`(실행 가능한 명세)로 이미 명세 우선 구조가 돌고 있고, **이 대회의 채점 기준에 맞춰 재단돼 있다**
3. ★ **채택하면 제출물이 오히려 약해진다.**
   이 대회는 *우리가* AI 지휘를 설계했다는 증거를 본다.
   **"BMAD를 썼습니다"는 활용이고, "왜 안 썼는지 판단했습니다"가 설계다.** 메인 카피가 대비시킨 바로 그 두 단어다

> **그래서 채택도 무시도 아닌 세 번째 선택지를 택한다 — 조사하고, 인용하고, 안 쓴 이유를 쓴다.**
> AI 활용 기술 문서 **2.2(각 단계에서 사용한 도구와 그 이유)** 에 들어간다.
> 기성 프레임워크를 몰라서 자체 제작한 게 아니라 **비교 후 규모가 안 맞아 기각했다**는 서술은, 자체 파이프라인의 정당성을 오히려 강화한다.

### 4.5.3 커밋 규약 자동 검증 — **채택. 단 husky가 아니라 CI로** ★

`09_커밋_규약.md` 는 **심사 대상 산출물**인데 현재 강제 수단이 없다. 사람이 지키다 D+5쯤 무너진다.

**일반적 해법:** husky + commitlint (Node 기반 `commit-msg` 훅)

**우리는 이렇게 하지 않는다.**

| | husky + commitlint | **GitHub Actions 검증** |
|---|---|---|
| Node 의존 | 필요 (Unity/C# 프로젝트에 불필요한 의존) | 불필요 |
| 저장소 포함 | `.git/hooks` 는 **버전 관리 대상이 아니다** → 2인 간 전파 안 됨 | 워크플로 파일이 저장소에 보인다 |
| **심사자 가시성** | 보이지 않음 | **실행 이력이 그대로 증거가 된다** |
| 우회 | `--no-verify` 로 뚫림 | 뚫을 수 없다 |

→ **PR/푸시 시 커밋 메시지를 CI가 검증한다.** 정규식 몇 줄이면 된다.

```
^\[(AI|H|BAL|REV)\] (feat|fix|refactor|test|docs|chore|data)\(.+\): .+
```
+ 본문에 `의도:` 존재 여부 검사

> **이건 `05` §2.3의 CI 가드(core에 `UnityEngine` 금지)와 같은 철학이다.**
> "AI를 신뢰하는 대신 위반할 수 없는 경계를 CI로 설치한다" — 가드가 2개가 되면 그게 **일관된 방법론**으로 읽힌다.
> 그리고 규약 위반으로 **실패한 CI 실행 기록 자체가** 기술 문서 4장의 재료가 된다.

### 4.5.4 [Game-UI-Reference-Cli](https://github.com/SillyToolValley/Game-UI-Reference-Cli) — **조건부 채택 (로컬 인덱싱 한정)**

| 기준 | 평가 |
|---|---|
| 시기성 | 커밋 9개, 최근 활동 없음. 다만 **기능이 고정적이라 노후화 위험이 낮은 종류** |
| 볼륨 | ✅ Python 3.10+, **로컬 인덱싱은 의존성 0** |
| 신뢰성 | 공개 지표(star 1 / fork 0)는 낮음 → **§4.6 참조. 이 도구에는 결정적 기준이 아니다** |

MIT. 용도는 게임 UI 레퍼런스 인덱싱 + 대조표(contact sheet)·매니페스트 생성.
오토배틀러의 **로스터 선택 / 상점 / 보드 배치 / 전투 / 결과** 5개 화면 레퍼런스가 실제로 필요하므로 용도 자체는 유효하다.

**채택 범위를 자른다.**

- ✅ **로컬 인덱싱(`scan-local`)** — 의존성 0, 손으로 모은 캡처를 정리하는 용도
- ⏸ **브라우저 수집(`collect --browser`)** — Playwright+Chromium 설치가 필요하고, 우리가 필요한 레퍼런스 물량이 그만큼 크지 않다. 수동 수집이 더 빠르면 생략
- 동반 스킬(`game-ux-ui-design`, 주석 와이어프레임 생성)은 **UI 설계 단계도 AI 파이프라인에 포함시킬 수 있는 카드**다 → 기술 문서 2.1(전체 워크플로)의 커버 범위가 넓어진다

> 채택 시 `14_에셋_라이선스.md` §3(오픈소스)에 MIT로 기재한다.

### 4.6 ★ 평가 기준 보정 — 세 기준은 블래스트 반경으로 가중치가 달라진다

§4.5.4를 처음에 "신뢰성 미달"로 기각했는데, **기준을 기계적으로 적용한 오류였다.**

| 도구 성격 | 신뢰성의 무게 | 이유 |
|---|---|---|
| **산출물에 실려 나가는 것** (에셋 팩, 런타임 라이브러리) | **결정적** | 라이선스·버그가 제출물에 그대로 박힌다. 되돌리기 비싸다 |
| **빌드 파이프라인에 들어가는 것** (GameCI) | 높음 | 깨지면 배포가 막힌다 |
| **개발 시점에만 로컬에서 도는 읽기 전용 도구** | **낮음** | 실패해도 손해가 "안 쓰면 그만". 산출물에 흔적이 없다 |

→ 앞으로 도구를 평가할 때 **시기성·볼륨·신뢰성에 더해 "실패하면 무엇이 망가지는가"를 먼저 묻는다.**
star 수가 낮다는 것은 위험의 *지표*이지 위험 그 자체가 아니다. 블래스트 반경이 0이면 지표도 무의미해진다.
