## 1. 요약 — AI는 무엇을 했고 사람은 무엇을 했는가

### 1.1 역할 분담

```
사람       : 무엇이 좋은 밸런스인가를 정의한다 (지표 M1~M7 · 목적함수 D)
           : 무엇을 AI에게 맡기지 않을 것인가를 정한다
           : AI 산출물의 채택·기각
AI(Claude) : 문서·코드 생성, 스펙 대조, 설계 감사
알고리즘    : 파라미터 탐색 (Optuna · SALib) — LLM이 아니다
게임 런타임 : AI 없음
```

**경계가 실제로 지켜졌는지는 저장소가 말한다.**

| CI 가드 | **6종.** 사람이 지켜야 하는 규칙보다 **어길 수 없는 규칙**이 낫다 |

### 1.2 한 줄 요약

> **AI에게 코드를 짜게 한 프로젝트가 아니라,
> 무엇을 검증할지 정의하고 그 검증을 자동화한 프로젝트다.**

9일 동안 이 문서가 반복해서 부딪힌 문제는 하나다 —
**AI 는 "안 되는 것"보다 "되는 것처럼 보이는 것"을 훨씬 잘 만든다.**
컴파일되고, 테스트가 통과하고, 지표가 숫자를 뱉는데 **아무 일도 안 일어나거나 틀린 걸 재고 있다.**
그래서 검증 기준을 **여섯 번** 끌어내렸고(4.3), 그 과정이 이 문서의 실체다.

★ 그리고 그 여섯 번을 늘어놓고 나서야 보이는 것이 하나 있다.
**같은 문장이 다섯 번 반복됐다 — *"없다"와 "못 읽었다"가 화면상 같았다.***
이건 사례가 다섯 개라는 뜻이 아니라 **검증 방식에 구조적 사각이 있다**는 뜻이고,
그 사각을 절차로 바꾼 것이 이 프로젝트가 AI 를 다루며 배운 가장 실질적인 것이다(4.3 말미).

### 1.3 사용한 AI 도구

**Claude (Claude Code)** 하나다. 상세 활용 내역은 8.4.
탐색에 쓰는 Optuna·SALib 는 **LLM 이 아니라 수치 최적화 라이브러리**이고, 그 구분이 2장의 요점이다.

## 2. AI 개발 파이프라인 구조 🔴 요강 필수 — "구조 설명"

### 2.1 전체 워크플로

```
 ┌── 사람 ────────────────────────────────────────────────┐
 │  "무엇이 좋은 밸런스인가" 를 정의한다                     │
 │     → 지표 M1~M7 · 만족도 함수 · 목적함수 D              │
 └───────────────────┬────────────────────────────────────┘
                     │  (기계가 읽을 수 있는 형태로)
 ┌───────────────────▼────────────────────────────────────┐
 │  /core   순수 C#. 전투·런 루프. UnityEngine 참조 불가     │
 │  /sim    콘솔 앱. params.json → metrics.json            │
 │  /tune   Python. Morris 스크리닝 → Optuna 탐색           │
 │  /unity  렌더링. 이벤트 로그를 재생만 한다                 │
 └───────────────────┬────────────────────────────────────┘
                     │  balance.json (verdict · D · provenance)
 ┌───────────────────▼────────────────────────────────────┐
 │  사람이 판정한다 → [BAL] 커밋 또는 기각                   │
 └────────────────────────────────────────────────────────┘
```

**층마다 다른 종류의 AI를 쓴다. 이걸 구분하는 게 이 문서의 핵심이다.**

| 층 | 무엇을 쓰나 | 무엇을 하나 |
|---|---|---|
| 정의 | **사람** | 지표·목적함수·기각 판정 |
| 생성 | **LLM (Claude)** | 코드·문서 생성, 스펙 대조, 설계 감사 |
| 탐색 | **알고리즘 (Optuna·SALib)** | 파라미터 탐색. **LLM이 아니다** |
| 실행 | **없음** | 게임 안에 AI가 없다 |

> ★ **이 루프에 런타임 LLM 호출이 0이다.**
> 개발 중 LLM도 **탐색이 아니라 정의와 판단**에만 쓴다 —
> *"어떤 값이 좋을까"* 를 LLM에게 묻지 않는다. 그건 4,320 빌드를 전수로 도는 시뮬이 답한다.

### 2.2 각 단계에서 사용한 도구와 그 이유

> **표준 수치 도구는 가져다 썼고, 무엇을 최적화할지는 우리가 정의했다.**

| 단계 | 채택 | 왜 |
|---|---|---|
| 전역 민감도 | **SALib (Morris)** | 31개 축 중 어디를 탐색할지 **측정으로** 고른다. 손으로 고르면 그게 곧 편향 |
| 파라미터 탐색 | **Optuna (CMA-ES + ASHA)** | ask-and-tell 로 외부 프로세스(`sim`)를 구동. 샘플러는 **Morris 결과가 골랐다** |
| 목적함수 | **직접 작성** | 디렉팅 층의 산출물이라 남의 구현 뒤에 숨기면 안 된다 |
| 지표 `M1`~`M7` | **직접 작성** | 같은 이유 |

**기각 목록이 채택 목록보다 중요하다.**

| 기각 | 사유 |
|---|---|
| **LLM을 최적화기로** | 4,320 빌드를 결정론으로 도는 데 확률적 생성기가 낄 자리가 없다. **재현이 안 된다** |
| **BMAD / Spec Kit** | 에이전트 워크플로 프레임워크. 2인 9일에 **프레임워크 학습 비용이 산출물을 넘는다** |
| **CMAES.NET** | 2020년 이후 방치(★11). 밸런스 루프 전체가 여기 얹히는데 **블래스트 반경이 너무 크다** |
| **OpenSpiel** | 게임이론 연구용. 우리 문제는 PvE 단일 플레이어라 **적용 조건이 안 맞는다** |
| **FixedMathSharp** | 결정론용 고정소수점. **우리는 전부 정수 연산이라 필요가 없었다** |
| **만족도 함수 라이브러리** | Derringer–Suich 는 20줄이다. **의존을 늘릴 이유가 없다** |

### 2.3 단계 간 산출물 연결

**층 사이를 파일로 잇는다.** 프로세스 경계를 파일로 그으면 한쪽이 죽어도 결과가 디스크에 남고,
심사자가 **각 단계를 따로 재현**할 수 있다.

```
/data/*.json      ──→  sim  ──→  metrics.json  ──→  tune  ──→  optuna-*.json
      ▲                                                            │
      └──────────  사람이 [BAL] 커밋으로 반영  ←──────────────────────┘
                            └→ balance.json (저장소에 남는 스냅샷)
```

**`balance.json` 의 `provenance` 가 이 사슬을 닫는다.**

```json
"provenance": {
  "simCommit":     "a4a10ab",
  "dataHash":      "sha256:1fc051da93a5866…",
  "overridesHash": "none",
  "seeds":         [1, 2, 3, 4, 5],
  "runsExecuted":  21600,
  "crnEnabled":    true
}
```

> ★ **밸런스 리포트는 숫자보다 출처가 중요하다.**
> 이 블록이 있으면 *"이 커밋의 이 데이터로 이 시드에서 이 결과가 나왔다"* 가 **파일 하나로 완결된다.**
>
> `dataHash` 는 **덮어쓰기를 적용한 뒤**를 잰다. 앞을 재면 최적화기가 시도한 수천 번이
> **전부 같은 지문**을 갖는데, **리포트는 멀쩡해 보인다.**

## 3. AI 대상 주요 프롬프트 및 지시 사항 🔴 요강 필수

### 3.1 프로젝트 전역 규칙

**세션마다 자동으로 주입되는 `CLAUDE.md` 가 이 프로젝트의 상시 지시문이다.**
매번 다시 말하지 않아도 되는 것들을 여기 박아뒀다. 핵심 두 대목을 원문 그대로 옮긴다.

> **커밋은 사후 산출물이 아니라 설계 대상이다.**
> "AI에게 어떤 단위로 일을 시켰고, 어디서 사람이 개입해 판단했는가"가
> 커밋 메시지와 diff에 드러나도록 처음부터 커밋 전략을 짤 것.
>
> - 한 커밋 = 하나의 의사결정 단위
> - AI 생성분과 사람 수정분을 가급적 분리 커밋. **사람의 판단 지점이 로그에서 보여야 한다**
> - squash / force push 금지. 히스토리를 깎아내지 말 것
> - **시행착오도 남긴다.** 되돌린 커밋은 그 자체로 "AI를 어떻게 통제했는가"의 증거

> **예선에서 본선으로 넘어가는 유일한 자산은 파이프라인이다.** 게임도, 그 게임의 BM도 아니다.
> → AI 개발 파이프라인은 **장르 비의존적**으로 설계할 것.

**이 두 문단이 실제로 결과를 바꿨다** — 5장의 커밋 구조와 7장의 이식성은 전부 여기서 나왔다.

### 3.2 단계별 핵심 지시문 — 원문 인용

> ⚠️ **D+0~D+1 의 지시문은 소급 재구성이다.** 세션 로그를 남기기로 정한 게 D+1 이라
> 그 이전 원문은 없다. **원문이 없는 걸 원문인 척하지 않는다** — 그날의 결정 근거로 역추적한 것이다.
> D+2 이후는 실제 원문이다 (`docs/ai-log/`).

#### 지시의 성격이 날마다 달라졌다 — 이게 이 절의 요점이다

| 날 | 지시의 성격 | 원문 |
|---|---|---|
| D+0~1 | **탐색 방향 지정** | *"최적화 관점도 생각해서 **어떤 도메인 지식이나 방법**을 쓰면 좋을지 조사"* |
| D+1 | **공백 탐지 위임** | *"결정해줄 다른 사항이나 **기획의 공백**은 없는지 더 찾아봐"* |
| D+1 | **역할 경계 유지** | *"**팀원이 정할 부분**이지 않나, 일단 넘어가"* |
| D+3 | **판단 단위 통째 위임** | *"작업은 체크리스트 보고 **적절한 순서로 알아서** 진행 / 커밋은 주기적으로 작은 단위로 쪼개서 올려"* |
| D+3 | **범위·순서 조정** | *"인게임 씬으로 보려면 **어느 정도의 단계가 남았지?**"* |
| D+3 2회차 | **판단 회수** | 미결 3건을 표로 올리자 **AI 가 이미 구현해둔 해석(`M4`)을 버리는 결정**을 내렸다 |
| D+5 | **증상 + 원인 후보 동봉** | *"적이 죽으면 스프라이트만 꺼지는데, AI 가 가장 가까운 놈을 체크하니 걔네를 적으로 보고 안 움직인다"* |
| D+7 | **위임 + 검증 범위 지정** | *"팀원 작업분 올라왔을거임, **충돌이나 기타 버그 주의해서** 병합진행하고 메인에 푸시"* |
| D+7 | **사실관계 되물음** | *"쓰는 데도 없지 않니?"* / *"우리 스테이지가 총 6개야"* |
| D+8 | **새 루프 신설 + 근거 자진 명시** | *"스테이지별 클리어율도 기록할 수 있음?"* → *"**대회 특성상 이런 사후관리에도 신경을 쓰면 긍정적 요소로 볼 것 같아서**"* |
| D+8 | **검증 가능성 선확인** | *"웹빌드 배포해야 전송확인 가능한거?"* |
| D+8 | **형식적 충족 캐묻기** | *"고지를 저렇게 숨겨도 무방한거임? 몰라서 물어보는거"* |

> ★ **지시의 성격이 뒤로 갈수록 한 층 올라갔다.**
> D+3 2회차까지가 *"판단 회수"* 였다면, D+8 의 두 질문은 **산출물이 아니라 판정 자체를 겨눈다.**
>
> *"웹빌드 배포해야 전송확인 가능한거?"* 는 기능이 아니라 **"이걸 어떻게 확인하느냐"** 를 물었고,
> 답하는 과정에서 **에디터 플레이도 실측 데이터에 섞인다**는 사각이 드러나 `bb7bcd1` 이 나왔다.
> 질문이 없었으면 개발자가 돌린 판이 심사자 데이터인 척 쌓였을 것이다.
>
> *"고지를 저렇게 숨겨도 무방한거임?"* 은 **AI 가 이미 완료로 표시한 항목**을 겨눴다.
> 결과는 3.3 #12 로 이어진다 — **요구를 문자 그대로 충족했는데 목적은 달성되지 않은 상태**였다.
>
> **두 질문 다 "틀렸다"고 하지 않았다.** *"이거 맞나"* 라고만 물었고, 그 물음이 판정을 뒤집었다.

> ★ **첫 지시가 *"어떤 라이브러리를 쓸까"* 가 아니라 *"어떤 도메인 지식을 쓸까"* 였다.**
> 그 한 단어 차이가 `17_최적화_방법론.md` 를 만들었고, 거기서 CRN·축차 반감법·Morris·
> Derringer–Suich 만족도 함수가 나왔다. **도구를 물었으면 도구 목록이 나왔을 것이다.**

> ★ **D+3 의 *"알아서 진행"* 은 위임이지 방임이 아니다.**
> 같은 세션에서 사람이 판단한 건 **셋뿐**이었고, 전부 *"멈춰라"* 계열이다 —
> *"팀원 체크리스트를 네가 갖고 있으면서 왜 묻느냐"*(AI 산출물 1건 되돌림),
> *"브랜치 정리는 마지막에"*(되돌리기 어려운 작업의 시점 조정),
> *"인게임 씬으로 보려면?"*(체크리스트 순서를 무시하고 **화면을 먼저** 뚫게 만든 질문).
>
> **마지막 것이 결정적이었다.** AI 는 체크리스트대로 `P4`(밸런스 루프)로 갈 참이었는데,
> 사람이 화면을 물었고 그 결과 **`sim` 결과 == 게임 결과 등식이 실측으로 확인**됐다.
> 그 등식 위에 이 프로젝트의 밸런스 수치 전체가 서 있었는데 **그때까지 확인된 적이 없었다.**

>
> ★ **뒤로 갈수록 실패의 층이 올라간다는 게 이 표의 진짜 내용이다.**
> 1~6 은 *"판단이 기울었다"*, 7~11 은 *"틀린 걸 재거나 덜 확인했다"*, 12~14 는
> *"고친 방법·형식·판정 자체가 틀렸다"* 다. **AI 를 오래 쓸수록 실패가 더 위쪽에서 일어난다** —
> 코드는 점점 맞아 가는데, 틀리는 자리가 **"무엇을 통과로 볼 것인가"** 로 올라간다.
> 그래서 이 프로젝트에서 사람이 마지막까지 놓지 않은 것이 **검증 기준 자체**였다(4.3).

## 4. 사람이 개입한 지점과 그 판단 기준

### 4.1 AI에게 맡기지 않기로 한 영역

| 영역 | 왜 |
|---|---|
| **무엇이 좋은 밸런스인가** (지표·목적함수) | 이걸 넘기면 **AI 가 자기 채점표를 만든다.** 디렉팅 층의 산출물이다 |
| **구조 수정** (데이터의 형태를 바꾸는 것) | 최적화기는 **값만 바꾸지 구조를 못 바꾼다.** 그 경계가 곧 저작 판단이다 |
| **관문 난이도** (적 배치·스탯) | 저작이 정한 것. 기계에 넘기면 게임이 *"통계적으로 적절한"* 쪽으로 밀린다 |
| **최적화기 제안의 채택** | 기계는 제안하고 사람이 판정한다. `balance.yml` 도 **자동 커밋하지 않는다** |
| **측정 모델의 가정** | `M5` 의 조작 시간 상수를 `/data` 가 아니라 코드에 둔 이유 — 4.2 참조 |
| **사람 플레이 데이터로 밸런스를 자동 반영하는 것** | D+8 에 관측 루프를 만들면서 **같이 배제했다.** 표본이 몇 판인데 그걸로 `/data` 를 고치면 **노이즈를 밸런스로 승격시킨다.** `[BAL]` 커밋은 사람이 넣는다는 규칙이 그대로다 |

> ★ **마지막 항목은 "만들 수 있는데 안 만든 것"이라 성격이 다르다.**
> 수집 파이프라인이 이미 있으므로 자동 반영은 코드 몇 줄이다. **쉬워서 더 위험하다** —
> 돌아가는 것처럼 보이고, 틀렸다는 사실이 한참 뒤에 밸런스 붕괴로만 나타난다.
> **무엇을 안 자동화할지 정하는 것도 파이프라인 설계다.**

### 4.2 AI 산출물을 되돌린 사례 ★

#### ① 설계 추천 14건 중 6건이 뒤집혔다 (D+1)

> *"AI 추천은 전부 구현 비용·결정론 유지 비용·시뮬 속도 쪽으로 기울어 있었고,
> 사람 판단은 **게임으로서 성립하는가** 쪽이었다. 후자가 맞았다.
> **2×2 고정 배치는 오토배틀러가 아니라 숫자 비교다.**"*

**뒤집힘이 문서에 그대로 남아 있다.** 지우지 않은 게 증거다 (`06` §H 종결표).

#### ② `M4` 정의 — AI 가 구현해둔 해석을 사람이 버렸다 (D+3 2회차) ★★

D+3 에 AI 가 `M4`(지배 빌드 점유율)를 *"클리어의 절반을 가져가는 빌드 비율"* 로 구현하고
`_definitionPending` 을 리포트에 박아 사람에게 올렸다. **사람은 그 해석을 기각했다.**

| | |
|---|---|
| 기각 사유 | 분모가 전체 빌드 수라 **난이도를 고치면 `M4` 가 같이 떨어진다.** 기하평균 안에서 `M1` 과 싸운다 |
| 대체 | **상위 5% 빌드의 클리어 점유율** — `M1` 과 분리된다 |
| **그 판단이 옳았다는 증거** | 같은 날 `C2-B` 수정이 클리어율을 48% → 33% 로 내렸는데 **`M4` 는 흔들리지 않았다** |

#### ③ AI 가 자기 등록 근거를 뒤집었다 (D+3 2회차) ★★★

`M5`(1런 3~5분)가 최적화로 안 움직이자 AI 가 *"탐색 공간이 해를 표현하지 못한다"* 로 미결을 등록했다.
**적 14종 28축을 탐색 공간에 넣자는 안까지 냈다.**

**그 근거가 틀렸다.**

```
M5 는 전투 틱만 잰다   ← 구현이 스스로 "하한으로 읽는다" 고 적어뒀다
목표 3~5분은 전체 런    ← 05 §1.8 의 한 라운드 = 상점 + 배치 + 전투

실제:  전투 0.46분 + 6.91라운드 × 15초 = 2.19분   (목표 하단 근처)
```

> ★ **`d`=0.153 이라는 낮은 점수는 *"게임이 짧다"* 로도 *"비교 대상이 틀렸다"* 로도 똑같이 읽힌다.**
> 앞의 해석을 믿었으면 **이미 목표 근처인 전투를 6.5배 늘려** 영상 제약(`05` §1.8)까지 깨뜨렸을 것이다.
>
> **정정을 문서에서 지우지 않고 `<details>` 로 접어 남겼다.** 틀린 판단도 기록이다.

#### ④ AI 가 **자기 산출물을 완료로 오판**한 것을 질문 하나가 뒤집었다 (D+8) ★★★

①②③ 은 전부 *"AI 의 산출물이 틀렸다"* 는 이야기다. D+8 의 두 건은 층이 다르다 —
**산출물은 돌아갔고, AI 는 그걸 완료로 표시했다.** 뒤집은 것은 사람의 **질문**이다.

| | 질문 | 드러난 것 | 커밋 |
|---|---|---|---|
| **에디터 판 분리** | *"웹빌드 배포해야 전송확인 가능한거?"* | 답은 "아니오"인데 **그 사실이 곧 문제였다.** 에디터 플레이도 전송되므로, 개발용 판이 심사자 데이터에 섞인다 | `bb7bcd1` |
| **수집 고지 순서** | *"고지를 저렇게 숨겨도 무방한거임? 몰라서 물어보는거"* | **위치가 아니라 순서.** 수집은 첫 플레이부터 시작되는데 설정은 그 뒤에 열린다 — 고지가 항상 사후였다 | `7a748b5` |

> ★★★ **앞의 건이 특히 아프다.** 바로 직전 커밋(`fdfa52e`)에서 AI 는 **계획에 없던 `app_ver` 칸을
> 스스로 추가**했다. 이유는 *"재튜닝 전후 데이터가 섞이면 안 된다"* 였다 — 축이 빠지면 안 된다는 것을
> **알고 있었다.** 그런데 **더 자주 섞일 축(누가 플레이했나)은 못 봤다.**
>
> **칸을 만드는 것과 축을 다 세는 것은 다른 일이다.** 그리고 이건 `M1` 을 스테이지 축 없이 봐온 것과
> 정확히 같은 실수다 — **같은 프로젝트 안에서, 같은 날, AI 자신이 그 교훈을 적은 직후에 반복됐다.**
>
> ★ **두 질문 다 "틀렸다"고 말하지 않았다.** *"이거 맞나"* 라고만 물었다.
> **AI 가 완료로 판정한 것을 사람이 다시 여는 것** — 이게 4장 전체에서 사람이 한 일의 정확한 형태다.

#### 🔴 D+5 — 합격한 지표가 유일한 단서였다

`M7` 은 **타임아웃 비율**이고 목표는 `<5%` 다. 실측 1.67% — 합격이다. 그래서 아무도 안 봤다.

**그런데 이 게임엔 서든데스가 있다.** 시간이 지나면 반드시 누군가 죽으므로
**타임아웃은 구조상 0에 가까워야 한다.** 1.67% 는 *합격이지만 설명이 필요한 숫자*였다.

죽은 유닛이 보드 칸을 영구 점유하는 버그를 고치자 `M7` 은 **정확히 0.00%** 가 됐다.
**그 버그의 유일한 흔적이 이 지표였는데, 임계값이 그것을 합격으로 덮고 있었다.**

> ★ **여기서 바꾼 것은 값이 아니라 질문이다.**
> *"임계값 안에 있는가"* 대신 **"이 지표가 구조상 가져야 할 값은 무엇인가"** 를 먼저 묻는다.
> 구조상 0이어야 하는 지표에는 임계값을 걸지 않는다 — **0이 아닌 이유**를 묻는다.

그 둘은 **언제나 "일치"로 나온다.** 옛 파일이 서빙돼도 통과한다.
실제로 판별력이 있는 건 `data` 와 `wasm` **둘뿐**이었다.

> ★ **고친 검증 안에도 통과만 하는 항목이 절반 있었다.**
> 항목 수는 안심을 주지만 판별력을 주지 않는다. 넷 중 둘이 상수였는데
> **넷을 다 통과했다는 사실이 그걸 가렸다.**

여섯 단을 늘어놓고 보니 **표현만 다른 같은 사건**이 다섯 번 반복됐다.

> ★★★ ***"없다"와 "못 읽었다"가 화면상 같다.***
> 다섯 번 다 이 문장이다. **사례가 다섯 개라는 뜻이 아니라 검증 방식에 구조적 사각이 있다는 뜻이다** —
> 부재(不在)와 판독 실패가 같은 모양으로 도착하는데, **AI 는 둘 다 "없음"으로 보고한다.**

> "없는 것"으로 읽기 전에 "못 읽은 것"을 먼저 의심한다.** 다섯 번째를 가른 것도 그 습관이었다 —

|---|---|
| 파일이 오는가 · 크기가 맞는가 · 이름이 맞는가 | |
| 런이 도는가 (`RunManager` 를 코드로 호출) | **클릭이 버튼까지 도달하는가** |

> ★ **`RunManager` API 를 코드로 직접 부른 게 UI 를 통째로 우회했다.**
> `onClick.Invoke()` 도 마찬가지다 — 그건 `EventSystem` 을 건너뛴다.
> *"버튼 로직이 맞는가"* 는 매번 검증했지만 *"클릭이 버튼까지 도달하는가"* 는 **한 번도 검증한 적이 없었다.**
>
> ★ **그 전날 우리 로그에 *"코드로 돈다 ≠ 눌러서 된다"* 라고 적어두고 그대로 밟았다.**
> 규칙을 아는 것과 그 규칙이 이번에도 적용된다는 걸 알아채는 것은 다른 일이다.

수정은 `InputSystem.QueueStateEvent` 로 **실제 마우스 클릭을 주입해** 검증했다 — 화면 전환까지 확인했다.

**각 단계는 앞 단계가 통과한 뒤에야 보였다.** 미리 알 수 있었다고 쓰지 않는다 —
그건 사실이 아니고, **사실이 아닌 편이 덜 설득력 있다.**

> ★ 실례: `A-5` 디버프 *"매 틱"* 표기를 **산술로 검증**해 5초 전멸임을 보이고 되물은 건.
> *"확인 필요"* 로 넘기지 않고 숫자를 냈다.

## 5. 커밋 히스토리로 본 개발 과정

### 5.1 커밋 전략 설계 원칙

**요강이 커밋 기록을 요구한 건 결과물만 볼 거면 요구할 이유가 없기 때문이다.**
*"AI를 어떤 단위와 리듬으로 써서 개발했는지를 로그로 검증하겠다"* 로 읽고 **커밋을 설계 대상으로 삼았다.**

```
[주체] type(scope): 요약

의도: <왜 이걸 지금 이렇게 했는가>       ← 모든 커밋 필수
검증: <무엇을 근거로 통과라고 판정했는가>  ← [AI] [BAL] 필수
지표: <M값 before → after>              ← [BAL] [REV] 필수
근거: <시뮬 리포트 경로>                 ← [BAL] 필수
```

| 결정 | 왜 |
|---|---|
| 주체 태그를 **제목 맨 앞**에 | 트레일러는 `git log --oneline` 에서 안 보인다. **심사자가 한 번에 AI/사람 경계를 읽어야 한다** |
| `[BAL]` 을 `[AI]` 와 분리 | `git log --grep="\[BAL\]"` 하나로 **밸런스 히스토리 전체가 뽑힌다** |
| squash / force push 금지 | 히스토리를 깎아내지 않는다 |
| **시행착오를 남긴다** | 되돌린 커밋이 *"AI를 어떻게 통제했는가"* 의 증거다 |

**규약을 CI 가 강제한다.** `husky` 대신 CI 를 쓴 이유 — `.git/hooks` 는 버전 관리 대상이 아니라
**심사자에게 안 보인다. CI 는 로그에 남는다.**

> ⚠️ **인용할 때 같이 적어야 하는 것 — 규약을 우리 스스로 어긴 날이 있다.**

> **규약 위반을 규약 위반으로 지우면 앞뒤가 안 맞는다.**
> 이건 감점 요인이 아니라 **게이트가 실제로 작동한 증거**다 —
> *"사람이 지켜야 하는 규칙보다 어길 수 없는 규칙이 낫다"* 의 실증이고,
> 그 규칙이 **만든 사람에게도 똑같이 적용됐다**는 기록이다.

### 5.3 히스토리에서 읽히는 개발 리듬

```
[AI] 113   [H] 106   [BAL]  2   [REV]  2     총 288개 / 9일 (병합 65개 제외 223개)
저자별 : NullMa 164 · verpivia-1 59          (2026-08-08 D+8 기준)
```

**`[AI]` 와 `[H]` 가 거의 반반이다.** 코드는 대부분 AI 가 썼는데도 그렇다 —
**AI 산출물에 사람의 판단이 들어간 순간 `[H]` 로 넘어가기 때문이다**(규약 §1.1).

> ★ **D+3 시점엔 `[H]` 가 `[AI]` 의 1.6배였는데 D+8 엔 거의 같아졌다.**
> 사람이 덜 개입해서가 아니다 — **개입의 형태가 커밋에서 질문으로 옮겨갔다.**
> D+8 의 결정적 개입 둘(`bb7bcd1`·`7a748b5`)은 *"이거 맞나"* 라는 질문에서 나왔고,
> **질문 자체는 diff 를 남기지 않는다.** 그래서 이 프로젝트는 판단을 두 곳에 더 남긴다 —
> 커밋 메시지의 `의도:` 줄과 `20_기여기록.md`. **그 둘이 없으면 이 표는 "AI 가 대부분 했다"로만 읽힌다.**

**날짜별로 지시의 성격이 바뀐 게 로그에 보인다** (3.2 표와 대조된다):

| | 사람의 역할 |
|---|---|
| D+0~1 | 설계 판단 — 추천 14건 중 6건 뒤집음 |
| D+2 | 검증 요구 — *"진짜 되는 거 맞아?"* |
| D+3 | 범위 조정과 멈춤 — 판단 단위를 통째로 위임하고 **방향만** 잡음 |
| D+3 2회차 | **평가 기준 확정** — 목적함수를 닫고, 첫 `[BAL]` 을 판정 |
| D+5 | **증상 제보 + 원인 후보 동봉** — 규명은 맡기되 **어디를 볼지**를 좁혀줌 |
| D+7 | **위임 + 검증 범위 지정** — *"병합해라"* 가 아니라 *"충돌·버그 주의해서 병합"* |
| D+8 | **판정 자체를 겨눈 질문** — *"이거 확인 가능한거임?"* · *"이렇게 숨겨도 무방한거임?"* |

> ★ **D+3 2회차가 가장 되돌리기 어려운 층이다.** 목적함수는 그 뒤 수천 번의 최적화가 전부 딛고 서는 정의다.
>
> ★ **D+8 이 가장 값싼 층이다 — 그리고 그게 요점이다.** 두 질문은 각각 한 문장이었고
> 코드를 읽지 않았으며 *"틀렸다"* 고 말하지도 않았다. 그런데 **AI 가 완료로 판정한 것 둘을 뒤집었다.**
> 아흐레를 놓고 보면 사람의 개입 비용은 계속 내려갔는데 **개입이 닿는 층은 계속 올라갔다** —
> 설계 판단(D+0) → 검증 요구(D+2) → 평가 기준(D+3) → **판정의 유효성(D+8)**.

## 6. 비용·성능 관리

### 6.1 API 호출 설계

**게임 런타임의 LLM 호출은 0건이다.** 탐색은 Optuna 가 로컬에서 무료로 돈다.

| | 비용 |
|---|---|
| 게임 실행 | **0** — 브라우저에서 도는 WebGL 빌드. **게임 로직은 전부 클라이언트에서 돈다** |
| 런 종료 시 익명 통계 전송 | **0** — Cloudflare Workers·D1 **무료 티어 안.** 런당 요청 1회 (6.3) |
| 밸런스 루프 1회 | **0** — 4,320 빌드 전수 21,600런이 **1.3초**. GitHub Actions 무료 티어 안 |
| Morris 320평가 + Optuna 60시도 | **0** — 약 5분 |

> ⚠️ **정확히 쓴다 — D+8 에 서버가 하나 생겼다.**
> D+7 까지 이 표에는 *"서버가 없다"* 라고 적혀 있었고 그때는 사실이었다.
> D+8 에 운영 측정용 엔드포인트(Cloudflare Worker + D1)를 붙였으므로 **그 문장은 더 이상 맞지 않는다.**
> **`LLM 호출 0` 이라는 결론은 그대로다** — 그 엔드포인트는 행 하나를 넣고 집계를 돌려줄 뿐 AI 를 부르지 않는다.
> 브라우저 개발자 도구를 10초만 열면 드러나는 종류의 문장이라, 결론이 유지되더라도 **근거를 고쳐 적는다.**

> **처리량이 비용 설계의 전부였다.** 유닛-틱당 **0.017 µs** 로 예산(5 µs)의 **1/290** 이다.
> 그래서 *"밤에 CI 가 돌려두고 아침에 리포트를 본다"* 가 가능하다 —
> 여기가 느렸으면 밸런스 루프는 **설계만 있고 안 도는 것**이 됐다.

### 6.2 게임 밖의 서버 — 무엇을 보내고 무엇을 안 보내는가

`sim` 은 21,600런을 1.3초에 돈다. **사람 데이터가 이길 수 있는 싸움이 아니다.**
그래서 이 엔드포인트의 목적은 밸런스가 아니라 **`sim` 이 예측한 분포와 사람이 고른 분포를
나란히 놓을 자리를 만드는 것**이다.

> 🔴 **이 문서는 "사람 데이터로 밸런스를 잡았다"고 주장하지 않는다.** 그건 사실이 아니다 —
> 심사 기간에 모일 표본은 몇 판 수준이고, **표본 수를 한 번 물으면 무너지는 주장**이다.
> 정확한 주장은 **"예측과 실측을 대조하는 자리를 닫았다"** 이고, 그 이상은 쓰지 않는다.

| 설계 원칙 | 이유 |
|---|---|
| **응답을 기다리지 않는다** (코루틴 · 10초 타임아웃 · 실패 무시) | 여기서 한 번이라도 블로킹하면 네트워크가 느린 심사자의 화면이 멈추고, **그건 "서버가 느리다"가 아니라 "게임이 구리다"로 읽힌다** |
| **엔드포인트가 비어 있으면 전송하지 않는다** (기본값) | 설정을 빠뜨린 빌드가 나가도 게임은 평소대로 돈다. **안전한 쪽이 기본값이어야 한다** |
| **식별 정보를 안 보낸다** — 익명 GUID 하나 | 쿠키 없음·제3자 전송 없음. 같은 방문자의 여러 런을 잇는 것 외의 용도가 없다 |
| **수집 사실을 화면에 적는다** — 타이틀 하단 + 설정 | 요강 유의사항(고지)의 이행. **수집보다 먼저 보여야 해서** 타이틀에 뒀다(3.3 #13) |
| **에디터 플레이는 다른 이름으로 쌓인다** (`app_ver`) | 개발용 판이 섞이면 `M1` 은 **심사자의 클리어율이 아니라 개발자의 클리어율**이 된다(4.2 ④) |

**`RunManager` 는 전송 코드를 모른다.** 반대로 전송 쪽이 `RunManager.RunEnded` 를 구독한다 —
`IEventSink` 를 쓰기 전용으로 둔 것과 같은 발상이다. **측정이 게임을 못 건드리는 것을
약속이 아니라 구조로 만든다.** 이 파일을 지우면 측정만 사라지고 게임은 그대로다.

### 6.3 런타임 AI의 지연·실패 처리 — **해당 없음, 그리고 그게 결론이다**

*"안 썼다"* 가 아니라 **"쓰지 않기로 판단했다"** 다.

| 만약 런타임 LLM 을 넣었다면 | |
|---|---|
| 결정론 | **깨진다.** 같은 시드가 다른 결과를 낸다 → 밸런스 수치 전체가 의미를 잃는다 |
| 심사 | 요강이 *"별도 유료 라이선스 없이 실행 가능"* 을 요구한다. **API 키가 필요한 게임은 그 조건을 못 지킨다** |
| 비용 | 유료 API 비용은 참가자 부담이다 |

> ★ **AI 를 게임 안에 넣는 것과 AI 로 게임을 만드는 것은 다른 일이고, 이 대회가 묻는 건 후자다.**
> 대회 카피가 *"AI 를 활용하는 사람"* 이 아니라 **"AI 의 다음 단계를 설계할 디렉터"** 를 찾는다고 적혀 있다.

## 7. 재현성 및 확장성 ★ 본선 진출 어필

### 7.1 파이프라인 이식성

**갈아끼우는 건 두 개뿐이다: 「지표 목록」과 「전투 로직」.**

| 이식되는 것 | 장르 의존 |
|---|---|
| 공통 난수(CRN) · 만족도 함수 · 축차 반감법 · Morris · `/tune` 분리 | ❌ 없음 |
| 결정론 규칙 4종 + CI 가드 6종 | ❌ 없음 |
| `/data` 계약 구조 (코드에 상수를 안 박는다) | ❌ 없음 |
| 커밋 규약 + `[BAL]` 태그 | ❌ 없음 |
| `balance.json` `provenance` 계약 | ❌ 없음 |
| **관측 루프** (Worker + D1 · 지표 이름을 `sim` 과 맞춰 대조 가능하게) | ❌ 없음 |
| **검증 습관 — `null`·빈 값·`200` 을 "못 읽은 것"으로 먼저 의심** | ❌ 없음 (4.3) |
| 스킬 템플릿 5종 · `M3b` | ✅ 이 게임 전용 |

> ★ **마지막 두 줄이 D+8 에 추가됐고, 성격이 앞의 것들과 다르다.**
> 관측 루프는 **`/stats` 응답의 키 이름과 분모를 `sim` 지표와 똑같이 맞춰** 만들었다 —
> 이름이 갈리면 대조표를 손으로 맞추게 되고, 그러면 루프가 아니라 일회성 조사가 된다.
> **"예측과 실측을 같은 축에 놓는다"는 이 계약 자체가 장르에 안 묶인다.**
>
> 검증 습관은 코드가 아니라 **절차**인데, 이 프로젝트에서 가장 비싸게 얻은 것이라 같이 적는다.
> 다섯 번 밟고 나서야 규칙이 됐다(4.3).

**주장이 코드로 확인된다.** `/tune` 4개 모듈 중 **게임을 아는 건 `space.py` 하나뿐**이고,
나머지 셋(`evaluate`·`screen`·`optimize`)은 *"파라미터 이름과 범위"* 만 알고 **게임이 무엇인지 모른다.**
CI 가드가 그걸 강제한다 — `/tune` 이 전투 값을 계산하면 워크플로가 멈춘다.

#### ★★ 이식 가능한 **실패 사례** 하나 — 이게 더 값이 크다

축차 반감법(`R4`)의 저예산 단계를 만들려고 표본(빌드 수)을 줄였더니 **목적함수가 0 이 됐다.**

```
seeds=1 builds=200   D = 0.0000        seeds=1 builds=all   D = 0.6371
seeds=3 builds=200   D = 0.0000        seeds=3 builds=all   D = 0.6369
```

> **지표 셋(`M3a`·`M3b`·`M3c`)이 「빌드 공간」 위에서 정의돼 있었다.**
> 그 공간을 잘라내면 *"사장된 선택지"* 가 통계가 아니라 **자르는 위치의 함수**가 되고,
> 기하평균이라 그 하나가 전체를 0 으로 만들어 **기울기가 통째로 사라진다.**
>
> ★ **일반화: 지표가 표본 공간 자체 위에 정의돼 있으면 그 공간은 예산 축이 될 수 없다.**
> 오토배틀러 이야기가 아니다 — ***"다양성"* 을 재는 지표를 가진 모든 튜닝 루프에 걸린다.**
> **교과서에 없고 돌려보기 전에는 안 보이는 종류다.**

→ 예산 축을 **시드**로 옮겼다.

### 7.2 48시간 본선에서 이 방식이 어떻게 작동하는가

**48시간에서 가장 비싼 건 코딩이 아니라 밸런스 감(感) 잡기다.**
사람이 수십 판을 돌려보며 *"이거 너무 세네"* 를 감으로 잡는 데 통째로 하루가 간다.
**이 파이프라인은 그걸 CI 에 넘긴다.**

| 시각 | 무엇 | 누가 |
|---|---|---|
| **0h** | 주제 공개 | — |
| **0~2h** | 🔴 **지표 정의** — *"이 게임이 좋다는 게 무슨 뜻인가"* 를 `M1`~`Mn` 으로 | **사람.** 여기가 전부다 |
| 0~2h | 동시에 `/data` 스키마 확정 | 사람 + AI |
| 2~10h | `/core` 전투 로직 — **결정론 규칙 4종은 그대로 가져온다** | AI 주도 |
| 6h~ | `/sim` CLI · `/tune` — **`space.py` 만 새로 쓴다** | 거의 복사 |
| 10h~ | **밤새 CI 가 돈다** | 기계 |
| 다음날 | `balance.json` 하나를 보고 `[BAL]` 판정 | 사람 |
| 30h~ | UI·연출 — **밸런스가 이미 수렴해 있다** | 팀 |

**세 가지가 48시간에서 특히 강하다.**

| | |
|---|---|
| **지표를 먼저 정한다** | 나중에 정하면 *"이미 만든 게임에 맞는 지표"* 가 되어 아무것도 못 잡는다 |
| **`/data` 계약을 먼저 세운다** | 병렬 작업의 충돌면이 **JSON 하나로 줄어든다.** 2인이 같은 파일을 안 만진다 |
| **밸런스를 자는 동안 돌린다** | 48시간 중 **8시간은 어차피 잔다.** 그 시간이 계산 시간이 된다 |

> ★ **D+8 에 한 줄이 더 붙었다 — 관측 루프를 만드는 데 1.5시간이 걸렸다(설계 포함).**
> 48시간 안에서 1.5시간은 쓸 수 있는 값이고, 얻는 것은 **현장 시연·심사 중에 사람이 실제로
> 무엇을 고르는지**를 `sim` 예측과 같은 축에 놓는 자리다. 본선은 심사자가 직접 만지는 자리라
> 예선보다 표본이 유리하다. **다만 그때도 "표본이 적다"는 전제는 그대로 적는다**(6.2).

> ★ **예선에서 본선으로 넘어가는 자산은 게임이 아니라 이 순서다.**
> 본선은 주제가 현장 공개되는 별개 결과물이라 **이 게임은 한 줄도 안 쓰인다.**
> 넘어가는 건 *"지표를 먼저 정하고, 검증을 기계에 넘기고, 판정만 사람이 한다"* 는 구조다.
>
> ⚠️ **솔직히 적어둘 한계** — 이 방식은 **시뮬 가능한 게임**을 전제한다.
> 내러티브 중심이나 실시간 조작 정밀도가 핵심인 장르라면
> `M1`~`Mn` 을 세우는 첫 2시간이 훨씬 어렵고, 그때는 **파이프라인이 아니라 지표 설계 능력**이 시험받는다.

### 8.3 참고 문헌 — **코드 차용 없이 설계 근거로만 인용**

| # | 문헌 | 무엇을 가져왔나 |
|---|---|---|
| R1 | RuleSmith: Multi-Agent LLMs for Automated Game Balancing (arXiv 2602.06232) | 탐색/디렉팅 2층 구조 |
| R2 | α-Rank: Multi-Agent Evaluation by Evolution (arXiv 1903.01373) | *"평균 승률은 상대 분포에 오염된다"* 는 **문제의식만** |
| R3 | Derringer & Suich, 만족도 함수 | `M1`~`M7` → 기하평균 단일 점수 `D` |
| R4 | Successive Halving / Hyperband | 시드 예산 배분 (Optuna ASHA 로 구현) |
| R5 | Morris, Elementary Effects | 탐색 대상 선정 |
| R6 | Common Random Numbers | 파라미터 세트 비교 시 시드 공유 |

> ⚠️ **R2 는 "썼다"고 쓰면 사실과 다르다.** α-Rank 는 **다자 대전 평가 기법**이고
> 이 게임은 **PvE 단일 플레이어**라 적용 조건이 안 맞는다. **코드는 한 줄도 쓰지 않았고**,
> 가져온 건 문제의식 하나다 — 그게 `M4` 를 *"평균 승률"* 이 아니라
> **"상위 5% 빌드의 클리어 점유율"** 로 정의하게 만들었다.

### 8.4 사용한 AI 도구와 활용 내역 *(요강 유의사항)*

| 도구 | 용도 |
|---|---|
| **Claude (Claude Code)** | 기획 문서 작성, 설계 감사, 코어·시뮬레이터·UI 코드 생성, 밸런스 리포트 해석 |

**게임 안에는 AI 가 없다.** 런타임 LLM 호출 0건이고, 그건 누락이 아니라 판단이다 (6장).

**저장소의 커밋 태그가 AI/사람 경계를 그대로 드러낸다** — `git log --oneline` 한 번으로 읽힌다.

```
[AI] 113   AI가 생성하고 사람은 승인만 한 것
[H]  106   사람이 작성했거나 AI 산출물을 교정한 것
[BAL]  2   시뮬 리포트에 근거한 밸런스 데이터 패치
[REV]  2   되돌림
                                            (2026-08-08 D+8 · 병합 65 별도)
```

> ⚠️ **`Co-Authored-By: Claude` 트레일러는 팀원 표기가 아니라 도구 표기다.**
> `[AI]`·`[BAL]` 커밋에만 붙이고 `[H]` 에는 안 붙인다 — 그래야 기여 구분이 기계적으로 검증된다.
> 제출물 ⑤(팀원 롤 기술서)의 인원과 혼동하지 않도록 여기 명시해 둔다.
