## 2. AI 개발 파이프라인 구조

### 2.1 전체 워크플로

**재료 있음** — `05` §1.5 + `13` §1.3 + `17`.

```
요강 역산 → 스펙(문서) → /data 계약 → 코어 구현 → 헤드리스 시뮬
    → 지표 M1~M7 → 만족도 함수 D → 외부 루프 탐색 → 밸런스 패치 → 재시뮬 → 커밋
                                                    ↑
                                    사람: 목적함수 정의 · 결과 기각권
```

★ **강조할 지점**: 이 루프에 **런타임 LLM 호출이 0**이다. 개발 중 LLM도 탐색이 아니라 **정의와 판단**에만 쓴다.

### 2.2 각 단계에서 사용한 도구와 그 이유

**재료 있음** — `13` 전체 + `14` §3 + `17` §8.

**★ 이 절의 핵심은 채택 목록이 아니라 기각 목록이다.**

| 기각 | 사유 |
|---|---|
| BMAD / Spec Kit (SDD 프레임워크) | 볼륨 불일치 + **채택하면 "설계"가 아니라 "활용"으로 읽힌다** |
| FixedMathSharp | 설계로 부동소수점을 없앴다 — **의존성 대신 설계로 푼 사례** |
| OpenSpiel (α-Rank) | Windows 미지원 + 무겁다 + **PvE라 적용 조건이 안 맞는다** |
| CMAES.NET / Math.NET | 방치·부적합 → **외부 루프를 C#으로 짤 이유가 없다는 전제 전환으로 이어짐** |
| 만족도 함수 라이브러리 | 30줄이고, **목적함수는 우리 것이어야 한다** |
| LLM을 수치 최적화기로 | **LLM은 최적화기가 아니다** (`13` §1.2) |

★ **반드시 쓸 문장**: *"표준 수치 도구는 가져다 썼고, **무엇을 최적화할지는 우리가 정의했다.**"*
이 문장이 없으면 도구 목록만 남아 "활용"으로 읽힌다.

### 2.3 단계 간 산출물이 다음 단계 입력이 되는가

**재료 있음** — `/data/_schema/README.md` 가 실물 증거다.

```
08(스펙) → _schema(계약) → *.json(데이터) → core가 소비 → sim이 산출 → balance.json → tune이 소비
```

★ **`balance.json` 의 `provenance`(시뮬 커밋 해시 · 데이터 해시 · 시드)** 를 인용한다.
**밸런스 리포트는 숫자보다 출처가 중요하다**는 게 이 파이프라인의 성격을 보여준다.

## 4. 사람이 개입한 지점과 그 판단 기준

### 4.1 AI에게 맡기지 않기로 한 영역

**재료 풍부.**

| 맡기지 않은 것 | 이유 |
|---|---|
| **수치 최적화** | LLM은 최적화기가 아니다. gradient 없이 수십 차원을 헤맨다 |
| **목적함수 정의** | *무엇이 좋은 밸런스인가*는 정의의 문제지 계산의 문제가 아니다 |
| **`M4a`/`M4b` 설계** | 잘못 재면 최적화기가 **"모든 빌드가 밋밋하게 비슷해지는"** 쪽으로 달려간다 |
| **전투 감각 판단** | A 트랙 담당의 영역. `D-50`·`D-52`를 되돌려 보냈다 |
| **에셋 생성** | AI 생성 이미지·사운드 미사용(`D-19`). 스타일 일관성·라이선스 단순성 우선 |

### 4.2 AI 산출물을 되돌린 사례 ★

**최고의 재료는 `06` §H 종결표다** — 내 추천 14건 중 **6건이 뒤집혔고 표로 나란히 남아 있다.**

> *"내 추천은 전부 구현 비용·결정론 유지 비용·시뮬 속도 쪽으로 기울어 있었고,
> 팀원 판단은 게임으로서 성립하는가 쪽이었다. 후자가 맞았다.
> **2×2 고정 배치는 오토배틀러가 아니라 숫자 비교다.**"*

★ **AI가 낸 안이 최적화 지표에 과적합됐고 사람이 교정한 사례**로 서술한다. 이게 이 대회가 보려는 것이다.

### 4.3 검증 기준 — 무엇을 근거로 통과라고 판단했는가

**재료 있음.** 이 프로젝트의 통과 기준은 전부 **기계가 판정 가능한 형태**다.

| 층 | 기준 |
|---|---|
| 데이터 | `_schema` §6 로드 검증 15개. **실패하면 즉시 에러, 조용히 기본값으로 넘어가지 않는다** |
| 결정론 | **같은 시드 2회 실행 → 결과 해시 동일** (CI) |
| 경계 | `/core` 에 `UnityEngine` 금지 · `/core`·`/sim` 에 Python 의존 금지 (CI) |
| 커밋 | 메시지 규약 정규식 검증 (CI) |
| 밸런스 | `M1`~`M7` 전부 목표 구간 → 만족도 기하평균 `D`. **하나라도 0이면 전체 0** |

★ **"AI를 신뢰하는 대신 위반할 수 없는 경계를 CI로 설치한다"** — 가드가 4종이면 그건 **일관된 방법론**이다.

★ 실례로 인용: `A-5` 디버프 "매 틱" 표기를 **산술로 검증**해 5초 전멸임을 보이고 되물은 건.
*"확인 필요"로 넘기지 않고 숫자를 냈다.*

#### ★★ D+4 추가 — 검증 기준이 세 번 내려갔다 (이 장의 중심 서사)

| 날 | 기준 | 무엇이 그걸 깨뜨렸나 |
|---|---|---|

| D+3 | *"넣었는데 안 쓰이고 있었다"* — **쓰는 쪽에서 한 번 돌려본다** | 스킬 3개가 컴파일·테스트 통과인데 루프가 안 부른다 |
| **D+4** | ***"지표가 침묵한다"*** — **지표가 그걸 볼 수 있는 조건인지 먼저 확인한다** | 아래 4건 |

**D+4 의 4건 — 전부 "지표가 초록이다" 가 근거가 되지 않는 자리다.**

| 사례 | 왜 지표가 못 잡나 |
|---|---|
| 보호막 재충전 미구현 | 전투가 평균 3.4초라 **10초 주기가 오지 않는다.** `D` 가 0.0013 움직였다 |
| `conditionalBoost` 미구현 | **봇이 아이템을 안 산다**(`08` §6.1) — `M1`~`M7` 에 아예 안 나타난다 |
| `GrantShield` 상한 버그 | 겹치는 조합이 **한 번도 발생한 적이 없었다** (`C4-P2` 가 안 걸리고 있어서) |
| `sim` 지표 계층 | **테스트가 0 이었다.** 틀려도 숫자는 계속 나온다 |

> ★ **이 셋은 한 이야기다.** 검증을 *"컴파일된다"* → *"실행된다"* → *"쓰인다"* → *"측정 가능한 조건에서 쓰인다"*
> 로 밀어내린 기록이고, **각 단계는 앞 단계가 통과한 뒤에야 보였다.**
> 미리 알 수 있었다고 쓰지 않는다 — 그건 사실이 아니고, 사실이 아닌 편이 덜 설득력 있다.

## 7. 재현성 및 확장성 ★ 본선 진출 어필

> **`04` §④ 주의사항: "7.2는 사실상 본선 진출 심사에 대한 직접적 답변이다. 비중 있게 쓴다."**

### 7.1 파이프라인을 다른 프로젝트에 이식하려면

**재료 있음 — `17`이 통째로 이 절이다.**

★ **`17`의 6개 방법은 전부 장르 비의존이다.** 오토배틀러에 붙은 게 아니라 *"시뮬 가능한 게임이면 무엇에든"* 붙는다.

| 이식되는 것 | 장르 의존 |
|---|---|
| 공통 난수(CRN) / 만족도 함수 / 축차 반감법 / Morris / 메타게임 지표 / `/tune` 분리 | ❌ 없음 |
| 결정론 규칙 4종 + CI 가드 | ❌ 없음 |
| `/data` 계약 구조 (코드에 상수를 박지 않는다) | ❌ 없음 |
| 커밋 규약 | ❌ 없음 |
| 스킬 템플릿 5종·`M3b` | ✅ 이 게임 전용 |

→ **이식 시 갈아끼우는 건 「지표 목록」과 「전투 로직」뿐이고, 나머지는 그대로 간다.**

#### ★ D+4 — 그 주장이 코드로 확인됐다

`/tune` 4개 모듈 중 **게임을 아는 건 `space.py` 하나뿐**이다.
나머지 셋(`evaluate`·`screen`·`optimize`)은 *"파라미터 이름과 범위"* 만 알고 **게임이 무엇인지 모른다.**
CI 가드가 그걸 강제한다 — `/tune` 이 전투 값을 계산하면 워크플로가 멈춘다.

#### ★★ 이식 가능한 **실패 사례**가 하나 생겼다 (이게 더 값이 크다)

축차 반감법의 저예산 단계를 만들려고 표본(빌드 수)을 줄였더니 **목적함수가 0 이 됐다.**

```
seeds=1 builds=200   D = 0.0000        seeds=1 builds=all   D = 0.6371
seeds=3 builds=200   D = 0.0000        seeds=3 builds=all   D = 0.6369
```

> **지표 셋(`M3a`·`M3b`·`M3c`)이 「빌드 공간」 위에서 정의돼 있었다.**
> 그 공간을 잘라내면 *"사장된 선택지"* 가 통계가 아니라 **자르는 위치의 함수**가 되고,
> 기하평균이라 그 하나가 전체를 0 으로 만들어 **기울기가 통째로 사라진다.**
>
> ★ **일반화: 지표가 표본 공간 자체 위에 정의돼 있으면 그 공간은 예산 축이 될 수 없다.**
> 이건 오토배틀러 이야기가 아니다 — *"다양성"* 을 재는 지표를 가진 모든 튜닝 루프에 걸린다.
> → 예산 축을 **시드**로 옮겼다. 교과서에 없고 **돌려보기 전에는 안 보이는 종류**다.

### 7.2 48시간 본선에서 이 방식이 어떻게 작동할 것인가 🟡

**뼈대는 있으나 시나리오 문장이 아직 없다.** → **D+8까지 반드시 쓴다.**

**쓸 내용의 방향**

- 48시간에서 가장 비싼 건 **밸런스 감(感) 잡기**다. 이 파이프라인은 그걸 **CI에 넘긴다**
- 주제 공개 → **지표 정의(사람, 2시간)** → 코어 구현 → 시뮬 → 나머지는 자동
- **`/data` 계약을 먼저 세우는 것**이 48시간에서 특히 강하다 — 병렬 작업의 충돌면이 JSON 하나로 줄어든다
- ★ 예선에서 **넘어가는 자산은 게임이 아니라 파이프라인**이라는 점을 명시 (`05` §1.6)
