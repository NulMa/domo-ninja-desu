## 1. Unity MCP — "Connection revoked" / 도구 호출이 전부 실패

**환경:** Unity 6000.5.4f1 · `com.unity.ai.assistant@284c75a8d208` · Claude Code 2.1.220 · Windows 11

### 1.1 증상

- Claude Code 쪽 `/mcp` 에서는 `unity-mcp` 가 **연결됨으로 표시**된다
- 그런데 도구를 호출하면 **Connection revoked** 로 실패한다
- Unity `Project Settings > AI > Unity MCP`:
  - Bridge Status **Running**
  - Integrations → Claude Code **`Configured`**
  - 그러나 **`Connected Clients: No clients connected`**
- 재시작(Claude Code / Unity Editor / Unity Hub 전부)해도 동일

**즉, 양쪽 UI가 모두 "정상"이라고 말하는데 실제로는 안 붙어 있는 상태다.** 이게 진단을 오래 끈 이유다.

### 1.2 진짜 원인

Unity 콘솔에 답이 있었다. **경고(Warning)로 찍히기 때문에 에러만 보고 있으면 놓친다.**

```
Connection denied: previously rejected by user
  at Unity.AI.MCP.Editor.Bridge.ValidateAndApproveAsync (...) Bridge.cs:1245
```

> **연결이 "끊긴" 게 아니라, 과거의 거부(reject)가 저장돼 있어서 자동으로 차단되고 있었다.**

승인 창을 한 번 놓치거나 닫으면 그 조합이 **거부 상태로 굳는다.** 이후 재연결 시도는 **승인 창을 띄우지도 않고** 즉시 거부된다. 그래서 아무리 재시작해도 상황이 바뀌지 않는다.

### 1.3 승인 상태가 저장되는 곳

```
unity/Library/AI.MCP/connections-v2.asset
```

내용 (승인된 상태):

```yaml
Status: 1
ValidationReason: Approved by user from settings
Identity:
  ServerIdentityKey: Hash:a7865c71...      # relay_win.exe 의 SHA256
  ClientIdentityKey: Hash:af5bf1f1...      # claude.exe 의 SHA256
  CombinedIdentityKey: Hash:a7865c71...|Hash:af5bf1f1...
```

**★ 승인 단위가 "Claude Code"라는 이름이 아니라 실행 파일 두 개의 SHA256 해시 조합이다.**

여기서 두 가지가 따라 나온다.

| 함의 | 결과 |
|---|---|
| **Claude Code 나 relay 가 업데이트되면 해시가 바뀐다** | 승인이 무효가 되고 **다시 승인해야 한다.** "어제까진 됐는데"의 정체 |
| `Library/` 는 `.gitignore` 대상이다 | **승인 상태는 커밋되지 않는다.** 팀원은 자기 PC에서 따로 승인해야 한다 |

### 1.4 해결 절차

**순서대로.** 3번이 핵심이고, 1~2번은 3번을 방해하는 잔재를 치우는 단계다.

1. **Unity 콘솔에서 원인 확인**
   경고 필터를 켜고 `Connection denied: previously rejected by user` 가 있는지 본다.
   있으면 이 절차가 맞다. 없으면 다른 문제다(§1.6).

2. **좀비 relay 프로세스 정리** (선택, 상태가 꼬였을 때만)

   ```powershell
   Get-Process relay_win -ErrorAction SilentlyContinue |
     Select-Object Id, StartTime | Format-Table -AutoSize
   ```

   ⚠️ **relay 가 여러 개인 것 자체는 정상이다.** 재연결 한 번에 2개가 뜬다.
   시각이 한참 오래된 것만 남아 있으면 정리한다.

   ```powershell
   Stop-Process -Name relay_win -Force
   ```

3. **거부 기록 삭제 — 실제 해결책**

   ```
   Unity 종료 → unity/Library/AI.MCP/connections-v2.asset 삭제 → Unity 재실행
   ```

   `Library/` 는 재생성되는 캐시라 지워도 안전하다.
   (Unity 를 켠 채로 지우면 메모리 상태가 다시 써버린다. **반드시 종료 후.**)

4. **Claude Code 에서 재연결**

   ```
   /mcp  →  unity-mcp  →  reconnect
   ```

5. **Unity 에서 승인 — ★ 여기서 대부분 실패한다**

   `Project Settings > AI > Unity MCP`

   > **`▶ Other Connections` 섹션이 기본으로 접혀 있다.**
   > 대기 중인 연결 요청이 이 안에 숨어 있다. 펼치지 않으면 승인 버튼을 볼 수 없고,
   > 그대로 두면 다시 §1.2 의 거부 상태로 굳는다.

   펼쳐서 대기 연결을 **Accept**.

6. **검증** — Claude Code 에서 도구를 실제로 호출해본다. UI 표시는 믿지 않는다.

   ```
   Unity_ManageEditor(Action="GetProjectRoot")
   ```

   기대값: `C:/Unity/NAN_pre/unity`

### 1.5 검증 통과 기록 (2026-08-02 02:46)

| 호출 | 결과 |
|---|---|
| `Unity_ManageEditor(GetProjectRoot)` | `C:/Unity/NAN_pre/unity` ✅ |
| `Unity_ManageEditor(GetState)` | `6000.5.4f1`, `IsCompiling: false` ✅ |
| `Unity_PackageManager_GetData(newtonsoft-json)` | `3.2.2` 설치 확인 ✅ |

### 1.6 원인이 아니었던 것 (같은 길로 다시 들어가지 말 것)

진단 중 의심했다가 **아닌 것으로 확인된** 것들이다. 기록해두지 않으면 다음에 또 여기서 시간을 쓴다.

| 의심 | 확인 방법 | 결과 |
|---|---|---|
| 프로젝트 폴더 rename 때문에 브릿지가 옛 경로를 본다 | `~/.unity/mcp/connections/bridge-*.json` 의 `project_path` 확인 | **경로 정확.** 원인 아님 |
| Unity 에디터 프로세스가 죽어서 stale 브릿지가 남았다 | 같은 파일의 `editor_pid` 를 `Get-Process` 로 대조 | **살아있음.** 원인 아님 |
| named pipe 가 안 만들어졌다 | `Test-Path \\.\pipe\unity-mcp-<id>` | **존재함.** 원인 아님 |
| relay 프로세스가 2개라서 짝이 안 맞는다 | 전부 kill 후 재시도 | **해결 안 됨.** 재연결하면 어차피 2개가 뜬다 — 정상 동작이다 |
| Figma MCP 와 동시 연결이 충돌한다 | — | **불필요했다.** 둘 다 붙은 상태로 정상 동작 중 |
| `SignatureValid: 0` (서명 검증 실패) | `connections-v2.asset` 확인 | 승인된 연결에도 `0`. **차단 요인 아님** |

### 1.7 팀원 안내 (한 줄 요약)

> Unity MCP 가 "연결됐다는데 안 되면", `Project Settings > AI > Unity MCP` 에서
> **`Other Connections` 를 펼쳐서 Accept.** 그래도 안 되면 Unity 끄고
> `unity/Library/AI.MCP/connections-v2.asset` 지우고 다시.

## 2. Python 호출 시 `python` 이 아무것도 안 함

**증상:** `python -c "..."` 이 `Python` 한 줄만 출력하고 끝난다.

**원인:** Windows 의 Microsoft Store 앱 실행 별칭(스텁)이 잡힌다. 실제 인터프리터가 아니다.

**해결:** `py` 런처를 쓴다.

```powershell
py --version      # 3.12.10
py -c "import json; print('ok')"
```

`/tune` (Python 최적화 루프)를 돌릴 때 스크립트·CI 문서에 `python` 이 아니라 **`py`** 로 적어둘 것.
간단한 JSON 검증 정도는 PowerShell 로도 된다.

```powershell
Get-Content data/economy.json -Raw | ConvertFrom-Json | Out-Null
if ($?) { "valid" }
```

## 3. GitHub — 이메일로 협업자 초대가 안 됨

**증상:** 개인 저장소에 이메일 주소로 collaborator 초대 시 REST API 가 **404**.

**원인:** 개인(user) 저장소의 collaborator API 는 **username 만 받는다.** 이메일 초대는 Organization 저장소 기능이다.

**해결:** 이메일로 username 을 먼저 찾는다.

```
GET /search/users?q=<email>+in:email
```

⚠️ 공개 프로필에 이메일을 노출한 계정만 검색된다.
그리고 **검색 결과가 그 사람이 맞는지는 기계가 확인해줄 수 없다.** 초대 전 본인에게 username 을 확인받을 것.

## 4. `.gitignore` 의 폴더명이 rename 을 따라가지 않음

**증상 없음 — 그게 문제였다.**

Unity 프로젝트 폴더를 `unity/` 로 rename 했는데 `.gitignore` 에는 옛 이름 기준 패턴이 남아 있었다.

```gitignore
/[Dd]omo_[Nn]inja-desu/*.csproj    # ← 죽은 패턴
```

→ `/unity/*.csproj` 로 수정.

**놓쳤으면 `Assembly-CSharp.csproj` 등 생성 파일이 첫 커밋에 통째로 들어갈 뻔했다.**
커밋 히스토리가 심사 대상인 프로젝트에서 첫 커밋에 자동 생성 파일이 섞이면 그 자체로 감점 요인이다.

> **규칙: 폴더를 rename 하면 `.gitignore` 를 즉시 grep 한다.**
> 경로 고정 패턴(`/` 로 시작하는 것)은 rename 에 침묵으로 실패한다.

## 배포본이 404 인데 로컬은 멀쩡하다 — 파일명 대소문자 (2026-08-03 / D+3)

### 증상

```
https://.../                         200
https://.../Build/WebGL.loader.js    404   ← 화면이 안 뜬다
```

`index.html` 은 열리는데 **로딩 화면에서 멈춘다.** 브라우저 콘솔에는 로더를 못 찾는다고만 나온다.

### 원인

```
index.html 이 부르는 것   Build/WebGL.loader.js
저장소에 올라간 것        Build/webgl.loader.js
```

**Windows 는 파일명 대소문자를 구분하지 않는다.** 예전 빌드가 소문자 `webgl.*` 를 만들었고
그 이름이 git 인덱스에 남아 있었는데, 새 빌드가 `WebGL.*` 를 만들어도
git 이 **"같은 파일"로 보고 이름을 갱신하지 않았다.**

**GitHub Pages 는 구분한다.**

### ★ 이게 위험한 이유

- **로컬에서 절대 재현되지 않는다.** 파일 탐색기로 열어보면 멀쩡히 있다
- `git status` 도 깨끗하다. 내용이 같으니 변경으로 잡히지 않는다
- **배포는 "성공"으로 끝난다.** 푸시도 되고 Pages 빌드도 통과한다

### 해결

인덱스에서 먼저 지우고 새 이름으로 다시 넣어 대소문자를 강제한다.

```bash
git rm -r --cached Build
rm -rf Build && cp -r <빌드산출물>/Build .
git add -A          # R  Build/webgl.loader.js -> Build/WebGL.loader.js
```

### 재발 방지 — **배포 후 URL 로 확인한다**

```bash
for f in "" "Build/WebGL.loader.js" "Build/WebGL.wasm.unityweb"; do
  curl -s -o /dev/null -w "%{http_code} $f\n" "https://nulma.github.io/domo-ninja-desu/$f"
done
```

> ⚠️ **GitHub Pages 반영에 1~2분 걸린다.** 푸시 직후 404 는 아직 판단할 수 없다.
> 실제로 이때도 45초 뒤엔 404, 90초 뒤엔 200 이었다 — **너무 일찍 보고 원인을 잘못 짚을 뻔했다.**

### 원인이 아니었던 것

| 의심 | 실제 |
|---|---|
| `.nojekyll` 누락 | 있었다. `_` 로 시작하는 파일도 없다 |
| `.unityweb` 확장자를 Pages 가 막는다 | 아니다. 이름을 고치니 200 |
| `decompressionFallback` 문제 | 무관하다. 그건 **받은 뒤** 푸는 단계다 |

## Unity MCP — `Play` 가 성공을 돌려줘도 컴파일된 게 아니다 (2026-08-08 / D+8)

### 증상

`Unity_ManageEditor { Action: "Play" }` 가 `{"success": true, "message": "Entered play mode."}` 를
돌려줬다. **컴파일 오류가 있는데도** 그랬다.

`Unity_GetConsoleLogs` 를 바로 읽으면 **빈 배열**이 온다 (`totalCount: 0`).
"Clear on Play" 로 지워진 뒤라 **오류가 있는데 없는 것처럼 보인다.**

→ 실제로는 `error CS1061` 하나 때문에 `DomoNinja.Unity.View.dll` 이 **38분 전 것 그대로**였고,
그 위에서 *"컴파일 오류 0"* 이라고 판단했다.

### ★ 왜 위험한가

**"컴파일된 것"과 "컴파일했다고 믿는 것"이 구분되지 않는다.**
이 저장소가 D+4 에 겪은 것(스프라이트 경로 추측)과 같은 모양이다 —
콘솔에 아무것도 안 뜨는데 화면만 옛날 코드로 돈다.

### 확인 방법 — **어셈블리 파일 시각을 본다**

콘솔이 아니라 산출물을 본다. 소스보다 오래됐으면 컴파일 안 된 것이다.

```bash
ls -la --time-style=+%H:%M:%S unity/Library/ScriptAssemblies/DomoNinja.*.dll
ls -la --time-style=+%H:%M:%S unity/Assets/Scripts/View/BoardView.cs
```

| 어셈블리 | 무엇이 들어가나 |
|---|---|
| `DomoNinja.Core.dll` | `core/` (UPM 로컬 패키지) |
| `DomoNinja.Unity.dll` | `Assets/Scripts/Runtime` |
| `DomoNinja.Unity.View.dll` | `Assets/Scripts/View` |
| `DomoNinja.Unity.UI.dll` | `Assets/Scripts/UI` |
| `DomoNinja.Unity.Editor.dll` | `Assets/Scripts/Editor` |

**고친 파일이 속한 어셈블리가 안 갱신됐으면 검증이 성립하지 않는다.**

### 새로고침을 강제하는 법

`Unity_ManageEditor` 에는 Refresh 액션이 없다. 대신:

```
Unity_RunCommand {
  Action: "execute_menu_item",
  MenuPath: "Assets/Refresh",
  Code: "public static class NoOp { public static void Run() { } }"
}
```

> ⚠️ **이 호출은 `UNEXPECTED_ERROR: No logs available` 를 돌려주는데, 그래도 새로고침은 된다.**
> 반환값을 믿지 말고 위의 어셈블리 시각으로 확인할 것.
> `Code` 는 안 쓰이지만 **비우면 `CODE_REQUIRED` 로 거부**되므로 아무 클래스나 넣는다.

### 원인이 아니었던 것

- **Auto Refresh 설정** — 꺼져 있지 않다. `Play` 를 부르면 새로고침 자체는 돈다
- **`Unity_RunCommand { Action: "execute" }`** — 어떤 형태로 코드를 넣어도
  `No logs available` 로 끝난다. 임시 에디터 스크립트에
  `[InitializeOnLoadMethod]` 를 붙이는 편이 확실하다 (도메인 리로드 때 돈다)
