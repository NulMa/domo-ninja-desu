### 1.1 `D-15` 밸런스 판정·적용 절차 ★ 구현 전에 필요

**"누가 언제 판정하고 무엇을 커밋하는가"** 가 비어 있었다. `17`은 방법론만 정했다.

```
① nightly CI → 전체 SH + Optuna → balance.json 아티팩트
② 사람이 balance.json 하나만 본다 → verdict: pass / fail
③ fail이면 violations 목록을 보고 판단
     ├ 파라미터 조정으로 될 것  → 최적화기가 제안한 값을 [BAL] 커밋
     └ 구조 문제               → 사람이 판단해 [H] 커밋 또는 스펙 개정
④ 재시뮬 → 나빠졌으면 [REV] 되돌림
```

| 항목 | 결정 |
|---|---|
| 적용 방식 | **`main` 직선 커밋.** PR 없음 — 2인 프로젝트에서 PR은 마찰만 는다 |
| 커밋 태그 | `[BAL] data(data): ...` — 본문에 **변경 전/후 `D` 값과 어긋난 지표**를 적는다 |
| 판정 주체 | **사람.** 최적화기는 값을 제안할 뿐 채택하지 않는다 |
| 되돌림 | `[REV]`. **되돌린 커밋을 지우지 않는다** — 그 자체가 기술 문서 4.2 재료 |
| 빈도 | D+7 집중 가동일에 최대. 그 전엔 하루 1회 |

> ★ **`[BAL]` 커밋 본문 템플릿을 고정한다.** 이게 기술 문서 5.2(대표 커밋 인용)에 그대로 실린다.
>
> ```
> [BAL] data(data): C3-A 보호막 획득량 80 → 65
>
> 의도: M3b에서 C3-A 선택률이 88%로 상한(80%)을 넘었다.
>       회피 보호막이 저체력 페널티를 과보상하고 있다고 판단.
> 검증: D 0.71 → 0.83 / M3b(C3) 88% → 67% / 나머지 지표 구간 유지
> 근거: balance.json @ sim a1b2c3d, seed 1..30, CRN on
> ```

### 2.3 ★ asmdef가 `D-12`를 코드로 강제한다

`05` §2.3에서 *"core에 `UnityEngine` 참조가 들어오면 CI로 빌드 실패시킨다"* 고 했는데,
**asmdef에 더 나은 수단이 있다.**

```json
// core/DomoNinja.Core.asmdef
{
  "name": "DomoNinja.Core",
  "rootNamespace": "DomoNinja.Core",
  "references": [],
  "noEngineReferences": true,     // ★ UnityEngine·UnityEditor 자체가 안 보인다
  "autoReferenced": false
}
```

> **`noEngineReferences: true` 면 컴파일러가 `UnityEngine` 을 아예 못 찾는다.**
> AI가 `Vector2`·`Debug.Log`·`Random.Range` 를 쓰면 **그 자리에서 컴파일 에러**가 난다.
> CI가 나중에 잡는 게 아니라 **작성 순간 막힌다.**
>
> ★ CI grep 검사는 **그래도 남긴다** — `dotnet` 빌드(Unity 밖)에서는 asmdef가 관여하지 않기 때문이다.
> **가드 두 겹**이 되고, 이건 기술 문서 4.3(검증 기준)에 그대로 쓴다.

### 2.4 asmdef 분할표

| asmdef | 참조 | 왜 나누나 |
|---|---|---|
| `DomoNinja.Core` | **없음** (`noEngineReferences`) | 의존 방향 강제. `sim`·`tune`이 Unity 없이 돈다 |
| `DomoNinja.Core.Tests` | Core, NUnit | 테스트가 런타임에 섞이면 빌드에 실려 나간다 |
| `DomoNinja.Unity` | Core | 게임 루프·입력·씬 부트스트랩 |
| `DomoNinja.Unity.View` | Unity | **이벤트 로그 재생 전담.** 연출을 고쳐도 로직이 재컴파일되지 않는다 (`A-9`) |
| `DomoNinja.Unity.UI` | Unity | UXML/USS. **UI 반복이 가장 잦으므로 반드시 분리** |
| `DomoNinja.Unity.Editor` | Unity, UI | 에디터 전용 코드가 빌드에 들어가지 않게 |

> **`View`와 `UI`를 나눈 이유가 실용적이다.** D+5~8에 이 둘을 가장 많이 고치는데,
> 합쳐두면 한 번 고칠 때마다 전투 코어까지 재컴파일된다. **하루에 수십 번이면 체감이 크다.**

### 2.5 경계 계약 — `Events/`

**`core` 와 `unity` 가 만나는 유일한 지점이다** (`A-9` 연출-로직 분리).

```
core   : 전투를 계산하고 이벤트 로그만 뱉는다.  (Move / Attack / Damage / Shield / Heal / Death / RoundEnd …)
unity  : 로그를 재생만 한다. 되감기·배속도 가능하다.
sim    : 로그를 아예 끄고 돌린다 (17 §7 처리량)
```

> **이 경계가 지켜지면**: 연출이 전투 시간에 영향을 못 주고 → `sim`과 Unity 결과가 갈라지지 않고 →
> `05` §2.3의 전제가 유지된다. **어기면 밸런스 검증 전체가 무너진다.**

## 4. 분담

### 4.1 나누는 축 — 파일 소유권

**기능이 아니라 디렉토리로 자른다.** 2인이 같은 파일을 만지면 `main` 직선 커밋이 깨진다.

| 트랙 | 담당 | 소유 경로 |
|---|---|---|
| **T1 엔진·파이프라인** | **사용자 + Claude** | `core/` `core.tests/` `sim/` `tune/` `.github/` |
| **T2 표현·콘텐츠** | **팀원** | `unity/` `data/encounters.json` `assets/` |
| **T3 문서·제출** | 분리 (§1.3) | `docs/` |

**왜 이렇게 나누나**

- **T1은 결정론·시뮬·최적화가 핵심**이고, 이 대회의 edge 축이다. Claude와의 협업 효율이 가장 높은 구간
- **T2는 감각 영역**이다. 팀원이 A 트랙 전투 규칙을 설계했고 역기획 3건을 파악하고 있다.
  **관문 저작(`encounters.json`)은 난이도 감각의 문제**라 시뮬로 대체되지 않는다
- **경계면이 하나뿐이다** — `Events/` 이벤트 로그 포맷. **팀원은 core 내부를 몰라도 Unity를 만들 수 있다**
