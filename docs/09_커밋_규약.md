# 커밋 규약 (`D-04`)

작성일: 2026-07-31 (D+0)
전제: `05_결정사항.md`, `03_전략분석.md` 5장

> **이 규약은 심사 대상이다.** 요강이 "커밋 기록 유지"를 명시했고(`01번` 103줄),
> 결과물만 볼 거면 히스토리를 요구할 이유가 없다. **AI를 어떤 단위와 리듬으로 지휘했는지를 로그로 검증하겠다는 뜻이다.**
>
> 그러므로 커밋 메시지는 "무엇을 바꿨는가"가 아니라 **"왜 그렇게 지시했는가"** 를 남긴다.
> 이 문서 자체가 나중에 AI 활용 기술 문서 **5.1(커밋 전략 설계 원칙)** 이 된다.

---

## 1. 형식

```
[주체] type(scope): 요약

의도: <왜 이걸 지금 이렇게 했는가>
검증: <무엇을 근거로 통과라고 판정했는가>
```

### 1.1 주체 태그 — 맨 앞에 둔다

**심사자가 `git log --oneline` 한 번으로 AI/사람 경계를 읽을 수 있어야 한다.**
그래서 주체를 본문 트레일러가 아니라 **제목 맨 앞**에 놓는다. 트레일러는 oneline에서 안 보인다.

| 태그 | 의미 |
|---|---|
| `[AI]` | AI가 생성하고 사람은 승인만 한 것 |
| `[H]` | 사람이 직접 작성했거나, AI 산출물을 교정한 것 |
| `[BAL]` | 시뮬 리포트에 근거한 밸런스 데이터 패치 |
| `[REV]` | 되돌림 |

- 혼합된 경우 **`[H]` 를 쓴다.** 사람의 판단이 들어간 순간 그 커밋의 성격은 사람 쪽이다
- `[BAL]` 을 `[AI]` 와 분리하는 이유: **밸런스 이터레이션이 이 프로젝트의 시그니처 루프**다.
  `git log --grep="\[BAL\]"` 하나로 밸런스 히스토리 전체가 뽑히고, 그게 그대로 문서의 전시물이 된다

### 1.2 type / scope

| type | 용도 |
|---|---|
| `feat` `fix` `refactor` `test` `docs` `chore` | 통상 의미 |
| `data` | `/data` JSON 값 변경 (밸런스 패치는 여기 + `[BAL]`) |

scope: `core` `sim` `unity` `data` `ci` `docs` `telemetry`

> `telemetry` 는 D+8 에 추가했다(`25` §6-1). 여섯 개 중 **배포되는 서비스**에 맞는 게 없었다 —
> `telemetry/` 는 게임 빌드에 안 들어가고 Cloudflare 에서 따로 돈다.
> **어휘를 늘리는 것보다 억지로 끼워 넣는 게 나쁘다** — scope 는 로그를 훑을 때
> "이 커밋이 어디를 건드렸나"를 알려주는 축이고, 틀린 축은 없는 축보다 해롭다.

### 1.3 본문

| 필드 | 필수 조건 |
|---|---|
| `의도:` | **모든 커밋 필수** |
| `검증:` | `[AI]` `[BAL]` 필수 — 무엇으로 통과 판정했는가 |
| `지표:` | `[BAL]` `[REV]` 필수 — M값 before → after |
| `근거:` | `[BAL]` 필수 — 시뮬 리포트 파일 경로 |

**언어는 한국어.** 심사자가 한국어 화자다. `type`/`scope`만 영문 관례를 유지한다.

## 2. 예시

```
[AI] feat(core): 전투 틱 루프와 타겟팅 구현

의도: 전투 규칙을 문장으로만 주고 내부 구조 설계까지 AI에 위임했다.
      대신 결정론 규칙(05번 §2.4)을 제약으로 함께 전달해 초기부터 지켜지게 했다.
검증: 같은 시드 2회 실행 결과 해시 일치. 8라운드 1000판 시뮬 무크래시.
```

```
[H] fix(core): 타겟팅 동률 시 List 인덱스 순서 의존 제거

의도: AI 산출물이 거리 동률 상황에서 순회 순서에 의존해 결정론이 깨졌다.
      규칙을 다시 지시해 재생성시키는 대신 사람이 직접 고쳤다.
      같은 실수가 반복될 지점이라 판단해, 재발 방지는 지시가 아니라 CI 검사로 옮긴다.
검증: determinism 회귀 테스트 추가 후 통과.
```

```
[BAL] data(data): 속성2 대보너스 18% → 14%

의도: M3에서 U21 등장률 86%로 상한(80%) 초과. 유닛 스탯이 아니라
      시너지 임계값이 원인이라고 판단해 시너지 쪽을 먼저 건드린다.
검증: 10000판 재시뮬. M1/M4가 목표 구간을 이탈하지 않는지 확인.
지표: M1 47%→45% / M3 최대 86%→71% / M4 31%→28%
근거: reports/2026-08-07T14-02.json
```

```
[REV] revert: "[BAL] 속성2 대보너스 18% → 14%" 되돌림

의도: M3는 해소됐으나 M1이 45%→28%로 급락했다. 속성2 시너지가 난이도 전체를
      지탱하고 있었다는 뜻이다. 단일 파라미터로 접근한 판단이 틀렸다고 보고
      되돌린 뒤, 유닛 스탯 쪽으로 방향을 바꾼다.
지표: M1 28% → 47% (복구)
```

> 위 `[H]` / `[REV]` 두 예시가 **기술 문서 3.3(실패한 지시와 그 수정 과정)과 4.2(AI 산출물을 되돌린 사례)의 재료**다.
> 이런 커밋은 감추는 게 아니라 **만들어 남기는 것**이다.

## 3. 커밋 단위

- **한 커밋 = 하나의 의사결정 단위.** "AI에게 시킨 한 덩어리" 또는 "사람이 개입해 고친 지점"
- **AI 생성분과 사람 수정분은 반드시 분리 커밋.**
  AI 결과를 먼저 커밋하고, 그 위에 사람 수정을 별도 커밋으로 올린다.
  → **AI가 무엇을 못 했는지가 diff로 드러난다.** 이게 이 대회에서 가장 값진 증거다.
  한 커밋에 합치면 그 정보가 영구히 사라진다
- 되돌릴 때는 `git revert`. **커밋을 지우지 않는다**
- 몰아서 커밋하지 않는다. 작업한 시점에 커밋한다 (`04번` 5.3 "개발 리듬"이 타임스탬프로 읽힌다)

---

## 4. 금지

- **squash 금지** (`--squash`, `rebase -i` 로 뭉개기)
- **force push 금지**
- 푸시된 커밋의 히스토리 변경 금지
- 커밋 메시지에 API 키·토큰 노출 금지

> `git pull --rebase` 는 **아직 push하지 않은 로컬 커밋에만** 쓴다. 이건 히스토리를 깎는 게 아니라 선형으로 유지하는 것이다.
> ⚠️ 단 rebase는 로컬 커밋 해시를 바꾼다. **문서에 인용할 해시는 push된 커밋에서만 고른다.**

## 5. 브랜치 전략

**`main` 직선 유지.** 심사자가 `git log` 를 한 번에 읽을 수 있는 것이 최우선이다.
브랜치를 많이 쓰면 히스토리가 얽혀 "리듬"이 안 보인다.

- `19_구현계획.md` §4.1에서 **파일 소유권**으로 분담했으므로(T1 `core`·`sim`·`tune`·`.github` / T2 `unity`·`encounters.json`·`assets`) 평시에는 `main` 직접 커밋
- D+5 이후 작업 영역이 겹치기 시작하면 **짧은 브랜치 + merge**. 그때도 squash merge는 쓰지 않는다

### 5.1 고정 브랜치 2개

| 브랜치 | 성격 |
|---|---|
| `main` | **유일한 통합 지점.** 항상 빌드 가능한 상태를 유지한다 |
| `gh-pages` | **WebGL 배포 전용. 사람이 커밋하지 않는다** — Actions만 쓴다 (§7 "생성 산출물") |

> ⚠️ `gh-pages` 에 손으로 커밋하면 빌드 산출물이 사람 히스토리에 섞인다.
> **이 저장소에서 히스토리는 심사 대상이므로, 기계가 만든 커밋과 사람이 만든 커밋은 브랜치로 격리한다.**

### 5.2 작업 브랜치 이름

```
<type>/<scope>-<요약>
```

**`type` 과 `scope` 는 §1.2 커밋 어휘를 그대로 쓴다. 새 단어를 만들지 않는다.**

| 예시 | |
|---|---|
| `feat/core-tick-loop` | 전투 틱 루프 구현 |
| `fix/sim-determinism` | 시뮬 결정론 깨짐 수정 |
| `data/encounters-stage2` | 스테이지 2 관문 저작 |
| `chore/ci-webgl-gate` | 배포 워크플로 |

규칙 4개:

- **영문 소문자 + 하이픈.** 커밋 메시지는 한국어지만 **브랜치 이름은 영문이다** — `github.ref_name` 이 Actions에서 아티팩트 경로·캐시 키로 쓰이는데 여기서 한글이 깨진다. 표현이 아니라 식별자라서 그렇다
- **슬래시는 하나만.** `feat/core/tick` 은 쓰지 않는다 — git ref는 디렉토리라 `feat/core` 브랜치와 **공존할 수 없다.** 나중에 어느 한쪽이 만들어지지 않는 사고가 난다
- **하루 이틀 안에 merge하고 지운다.** 오래 두면 `main` 직선 원칙이 무너진다
- **주체 태그(`[AI]`/`[H]`)는 브랜치 이름에 넣지 않는다** ★

> 마지막 항목이 중요하다. §3이 **"AI 생성분과 사람 수정분은 반드시 분리 커밋"** 을 요구하므로
> **정상적인 브랜치 하나에는 `[AI]` 와 `[H]` 커밋이 섞여 있는 게 맞다.**
> 브랜치에 주체를 붙이면 그 원칙과 정면으로 충돌한다. **주체는 커밋의 속성이지 브랜치의 속성이 아니다.**
>
> 같은 이유로 소유자(`t1/`·`t2/`)도 넣지 않는다. 파일 소유권으로 이미 갈라져 있어 이름이 더 알려주는 게 없다.

### 5.3 merge — `--no-ff` 를 쓴다

```bash
git merge --no-ff feat/core-tick-loop
git branch -d feat/core-tick-loop
```

**fast-forward를 막는 이유가 이 프로젝트에는 따로 있다.**

> `--no-ff` 는 merge 커밋을 남기고, 그 안에 **브랜치 이름이 기록된다.**
> 브랜치를 지워도 `Merge branch 'feat/core-tick-loop'` 는 히스토리에 영구히 남는다.
>
> → **"AI에게 시킨 한 덩어리"의 경계가 로그에서 보인다.** ff-merge를 하면 커밋만 일렬로 흡수되고
> 그 덩어리가 어디서 시작해 어디서 끝났는지가 사라진다. §3의 "커밋 단위" 원칙과 같은 목적이다.

⚠️ **squash merge는 금지**(§4). 규약으로만 두면 PR 화면에서 버튼 하나로 위반된다.
→ **저장소 설정에서 아예 꺼뒀다** (2026-08-02 적용, `Settings > General > Pull Requests`):

| 설정 | 값 | 이유 |
|---|---|---|
| `allow_squash_merge` | **false** | §4 금지 사항. 히스토리를 뭉갠다 |
| `allow_rebase_merge` | **false** | merge 커밋을 안 남겨 §5.3의 "덩어리 경계"가 사라진다 |
| `allow_merge_commit` | true | 유일하게 허용 |
| `delete_branch_on_merge` | true | §5.2 "merge 후 지운다"를 자동화. 이름은 merge 커밋에 남는다 |

> **규약을 문서가 아니라 설정으로 강제한 것이다.** `asmdef` 로 `D-12`를 강제한 것(`19` §2.3)과 같은 발상 —
> **사람이 지켜야 하는 규칙보다 어길 수 없는 규칙이 낫다.**

### 5.4 태그 — 마감 시점을 고정한다

| 태그 | 시점 |
|---|---|
| `submission` | **제출 시점 커밋. annotated 태그로 단다** |

```bash
git tag -a submission -m "NAN 2026 사전과제 제출 시점"
git push origin submission
```

> **이게 없으면 마감 이후에 커밋이 하나라도 더 생기는 순간 심사자는 어디까지가 제출물인지 알 수 없다.**
> 요강이 커밋 히스토리를 심사 대상으로 명시했으므로, **"여기까지가 제출물"이라는 기준점이 저장소 안에 있어야 한다.**
> 마감 직전 리허설(`D-23`, D+8 저녁)에서 태그까지 한 번 연습한다.

버전 태그(`v0.1` 등)는 **쓰지 않는다.** 9일짜리 단일 제출물이라 릴리스 개념이 없고, 태그가 늘면 `submission` 이 묻힌다.

## 6. AI 공동 저자 표기

`[AI]` 와 `[BAL]` 커밋에만 트레일러를 붙인다.

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

- **`[H]` 커밋에는 붙이지 않는다.** 그래야 기여 구분이 기계적으로 검증 가능해진다
- 이건 약관 **제4조 1항**(주요 AI 도구의 명칭과 활용 방식 고지 의무)을 **로그 레벨에서 이행**하는 것이기도 하다
- ⚠️ ⑤ 팀원 롤 기술서와 혼동될 여지가 있으므로, **기술 문서에 "Co-Authored-By는 팀원이 아니라 도구 표기"임을 한 줄 명시**한다.
  혼동 요소를 먼저 설명하면 오히려 신뢰가 올라간다

## 7. 저장소 위생 — 로그 가독성을 지키는 조치

커밋 규약을 아무리 잘 지켜도 **diff가 노이즈로 뒤덮이면 심사자는 읽지 않는다.**

| 항목 | 조치 | 이유 |
|---|---|---|
| `.gitignore` | Unity `Library/` `Temp/` `Logs/` `Build/` `obj/` `bin/` | **Library를 커밋하면 저장소가 수만 파일로 오염**되어 히스토리를 못 읽는다 |
| `.gitattributes` | `* text=auto` + Unity 자산 `binary` 지정 | 2인이 Windows에서 작업 → CRLF 차이로 **파일 전체가 변경으로 잡히는 사고** 방지 |
| 리포트 파일 | `reports/` 에 커밋 | `[BAL]` 커밋의 `근거:` 가 실제로 검증 가능해진다 |
| 생성 산출물 | WebGL 빌드 결과는 배포 브랜치/Actions로 분리 | 소스 히스토리에 빌드 산출물이 섞이지 않게 |

## 8. 대표 커밋 후보 표시

기술 문서 **5.2(대표 커밋 인용)** 에서 해시를 인용해야 한다. 나중에 찾으면 못 찾는다.

- 인용할 만한 커밋이 생기면 그 자리에서 `docs/commit-highlights.md` 에 한 줄 적는다
  (해시 + 왜 인용 가치가 있는지)
- 후보 유형: 최초 파이프라인 구축 / AI 산출물을 되돌린 지점 / 방향 전환 / 밸런스 루프가 처음 자동으로 돈 시점 / CI 가드를 추가한 지점
